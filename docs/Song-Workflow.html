Song-Workflow: vom Chord-Sheet zur LED-Show

Neue Songs werden nicht mehr von Hand in songs.cpp programmiert: Sheet + MP3 → Struktur in Takten → Show-Dramaturgie → generierter C++-Code. Jeder Song hat einen eigenen Ordner, jede Generierung wird als Version gesichert. Stand 03.10.2026.

1 · Überblick

Ein Song läuft ab dem Start-MIDI-Signal (CC 22 = Song-ID, Kanal 10) millisekundengenau durch. Alle Part-Dauern ergeben sich deshalb aus Tempo × Takten. Das Werkzeug rechnet sie aus, statt sie per Excel zu ermitteln.

DateiWerInhalt
song.yamldu (einmal vom Tool vorbereitet)Was musikalisch passiert: Tempo, Takte je Part, MIDI-Offset, Lyrics, Akkorde, Stimmungen, deine Effekt-Wünsche. Wird von keinem Werkzeug und nicht von Claude geschrieben.
show.yamlClaudeWie es aussieht: Szene, Farbschema, Geräte-Overrides, Akzente je Part (per Part-Name, ohne Takte)
generated.cppGeneratorder erzeugte C++-Code dieses Songs
versionen/<Zeit>/GeneratorKopie von song.yaml, show.yaml und generated.cpp bei jeder Generierung
src/songs_generated.cpp/.hGeneratorzusammengesetzt aus den generated.cpp aller Songs, nie von Hand ändern

Ein Ordner pro Song

songs/AllTheThingsSheSaid_v1/
  song.yaml            ← DEINE Datei: Takte, Stimmungen, Effekt-Wünsche
  show.yaml            ← aktive Show, von Claude abgeleitet
  generated.cpp        ← aktiver Code dieses Songs
  quelle/              ← Sheet (.txt) + MP3 (MP3 nicht in Git)
  audio-analyse/       ← analysis.yaml + analysis.png, jederzeit neu erzeugbar
  versionen/
    2026-10-03_1345/   ← song.yaml, show.yaml, generated.cpp, info.yaml

Das _v1 im Ordnernamen steht für die Fassung des Songs (Arrangement, Audio). Eine neue Fassung mit anderem Audio bekommt einen eigenen Ordner …_v2 und eine eigene Song-ID. Die Versionen der Show liegen darunter in versionen/.

In den Befehlen genügt der Anfang des Ordnernamens, Groß- und Kleinschreibung ist egal: songgen.py allthe.

2 · Einmalige Einrichtung

Die Python-Werkzeuge laufen in einer eigenen Umgebung tools/.venv (nicht versioniert). Einmal pro Rechner, in Git Bash im Projektordner:

python -m venv tools/.venv
tools/.venv/Scripts/python -m pip install -r tools/requirements.txt

Pakete: librosa (Audioanalyse), numpy, matplotlib (Analysebild), soundfile, pyyaml, openpyxl (Struktur-Tabelle). Getestet mit Python 3.9.

Zu Beginn jeder Sitzung

Git Bash im Projektordner öffnen und einmal eingeben:

export PYTHONIOENCODING=utf-8 PYTHONWARNINGS=ignore   # Umlaute richtig, librosa-Warnungen aus
PY=tools/.venv/Scripts/python                         # Abkürzung für alle Befehle unten

Alle Befehle in dieser Anleitung nutzen $PY. Ohne die Abkürzung schreibst du stattdessen tools/.venv/Scripts/python.

3 · Neuer Song Schritt für Schritt

Die vollständige Reihenfolge für einen neuen Song. Beispiel: „Such A Shame“ im Ordner SuchAShame_v1 mit Song-ID 32. In den Befehlen genügt der Anfang des Ordnernamens (such).

  1. Song-ID wählendu
    Eine Zahl von 1 bis 127. Das ist der MIDI-Wert von CC 22, mit dem der Song gestartet wird. 
    $PY tools/songgen.py          # zeigt die IDs der generierten Songs
    Handgeschriebene Songs stehen in src/main.cpp im switch (songID).
    • Ganz neuer Song: eine freie ID nehmen.
    • Neue Fassung eines alten, handgeschriebenen Songs: dieselbe ID wie bisher nehmen (z. B. 2 für Physical). Der Generator ersetzt dann den alten Aufruf, siehe Abschnitt 9, „Einen handgeschriebenen Song ersetzen“.
    Die Vorschau in Schritt 9 sagt, welchen alten Song eine ID ersetzen würde.
  2. Ordner und Struktur-Tabelle anlegenstruktur2song
    $PY tools/struktur2song.py SuchAShame_v1 --neu
    Legt songs/SuchAShame_v1/quelle/struktur.xlsx an, als Kopie der Vorlage songs/struktur-vorlage.xlsx (eine vorhandene Tabelle wird nie überschrieben). Du kannst die Vorlage auch von Hand kopieren. Name des Ordners: Songtitel ohne Leerzeichen plus _v1 für die Fassung. Eine spätere Fassung mit anderem Audio bekommt einen eigenen Ordner _v2 und eine eigene ID.
  3. MP3 ablegendu
    Nach songs/SuchAShame_v1/quelle/ kopieren: genau die Version, die live läuft, mit demselben Tempo und derselben Stille am Anfang. MP3s werden nicht versioniert. Ein Chord-Sheet braucht es nicht mehr.
  4. Struktur eintragen und song.yaml erzeugendustruktur2song
    struktur.xlsx in Excel ausfüllen – das Format ist das deines Songkalkulators: Midi-StartNummer, Interpret, Titel, BPM, StartTakt, StartBit und pro Part „Songpart“ und „bis takt“ (Erklärung in „Die Struktur-Tabelle“). Die Parts schneidest du so, wie du sie für die Show brauchst. Speichern, dann: 
    $PY tools/struktur2song.py such
    Schreibt songs/SuchAShame_v1/song.yaml mit Takten je Part, deinen Einschätzungen und einem Marker-Vorschlag (wenn Akkorde eingetragen sind).
    Alternative mit Chord-Sheet: sheet2song.py schätzt die Takte aus Sheet und MP3 (Abschnitt 4). Das passt nur, wenn das Sheet so geschnitten ist wie die Show, und ist bei langsamen Akkordwechseln unzuverlässig.
  5. Ergebnis prüfendu
    Die Tabelle in der Konsole lesen: pro Part von, bis, Takte sowie Start ms und Dauer ms ab dem Start-MIDI, so wie der Generator sie rechnet.
    • Stimmt die Summe der Takte mit dem DAW-Projekt überein?
    • Der erste Part ist um das StartBit kürzer (z. B. 0,875 statt 1 Takt).
    • Zeile Bund-Marker: Vorschlag ansehen.
    Kleine Fehler korrigierst du ab jetzt direkt in song.yaml. Läuft das Werkzeug noch einmal, schreibt es nur song.vorschlag.yaml daneben.
    Tabelle später geändert (Part vergessen, Takte verschoben): Werkzeug noch einmal laufen lassen und den Inhalt von song.vorschlag.yaml selbst in song.yaml übernehmen, komplett oder nur die geänderten Parts. Claude darf das nicht für dich tun. Achtung: Beim kompletten Übernehmen gehen Anmerkungen verloren, die du von Hand in song.yaml geschrieben hast. Wünsche, die bleiben sollen, gehören deshalb in die Spalte „Effektidee“ der Tabelle. Kommt ein Part dazu oder ändert sich ein Name, sag Claude Bescheid, damit show.yaml nachgezogen wird.
  6. song.yaml bearbeitendu
    Ab jetzt gehört die Datei dir, kein Werkzeug schreibt sie mehr. Der Reihe nach:
    • name und artist prüfen. Daraus wird der Lauftext „Titel by Interpret“.
    • midi_offset prüfen: Wie spät nach Takt 1 kommt das Start-MIDI?
    • Taktzahlen korrigieren, wo Schritt 5 Fehler gezeigt hat.
    • Parts aufteilen, wo sich die Musik im Part deutlich ändert, z. B. verse 2 (8 Takte) in verse 2a und verse 2b (je 4). Jeder Name muss eindeutig sein.
    • Pro Part deine Einschätzung ergänzen: energy 0–5, description, mood, instruments, solo.
    • Wo du den Effekt genau weißt, fest vorgeben: scene oder fx, scheme, tail, devices. Das hat immer Vorrang vor der Show.
    • markers: am Ende prüfen, ändern oder löschen.
    • Die Zeilen # ! … sind nur Hinweise des Tools und können weg.
    Alle Felder in Abschnitt 5.
  7. Audio analysierensonganalyze
    $PY tools/songanalyze.py such
    Schreibt audio-analyse/analysis.yaml und analysis.png. Das Tool hat keine Optionen. Meldet es Warnungen (Tempo-Drift, Formgrenze ohne Part-Grenze), die Ursache in song.yaml beheben und die Analyse wiederholen. Der Schritt braucht die MP3. Ohne Audio entfällt er, die Show entsteht dann nur aus deinen Beschreibungen. Details in Abschnitt 6.
  8. Show gestaltenClaude
    In Claude Code: „Gestalte die Show für SuchAShame_v1“. Claude liest song.yaml, die Analyse und das Analysebild, schreibt show.yaml und führt die Schritte 9 bis 11 selbst aus.
    Ohne Claude gibt es zwei Wege:
    • show.yaml von Hand schreiben, siehe Abschnitt 7.
    • Gar keine show.yaml: Dann braucht jeder Part in song.yaml entweder scene/fx oder energy. Aus energy wird eine Standard-Szene (0 Black, 1 Calm, 2 Verse, 3 Buildup, 4–5 Drop).
  9. Vorschausonggen
    $PY tools/songgen.py such --dry-run
    Zeigt die Timeline (case, Start, Dauer je Part), den Lauftext-Plan, Hinweise und Fehler. Es wird nichts geschrieben.
  10. Generierensonggen
    $PY tools/songgen.py such --note "erste Fassung"
    Schreibt generated.cpp, speichert eine Version unter versionen/ und setzt src/songs_generated.cpp/.h sowie den Block in main.cpp neu zusammen. Alle anderen Songs bleiben unverändert. Alle Optionen in Abschnitt 9.
  11. BauenPlatformIO
    pio run -e andresgit
pio run -e rinasbass -e lampe1 -e lampe2 -e scrollmatrix   # die übrigen Geräte
    src/definitions.h muss dafür nicht geändert werden.
  12. Flashendu
    Per USB, ein Gerät nach dem anderen: 
    pio run -e andresgit    -t upload --upload-port COM3
pio run -e rinasbass    -t upload --upload-port COM8
pio run -e lampe1       -t upload --upload-port COM11
pio run -e lampe2       -t upload --upload-port COM10
pio run -e scrollmatrix -t upload --upload-port COM9
    Oder alle Geräte auf einmal per WLAN: 
    python tools/build_ota.py --serve
    Danach ANDRESGIT mit gedrücktem Drehknopf einschalten. Ablauf und LED-Anzeigen stehen in docs/OTA-Update.html.
  13. Testendu
    Song per MIDI starten: CC 22 mit Wert = Song-ID auf Kanal 10. Prüfen:
    • Kommt der erste Part-Wechsel zu früh oder zu spät? Dann midi_offset anpassen.
    • Läuft die Show langsam auseinander? Dann bpm prüfen.
    • Sitzt ein einzelner Wechsel falsch? Dann die Taktzahl des Parts davor korrigieren.
  14. Nachsteuerndu Claude
    • Gefällt ein Part nicht: Claude einen Satz sagen wie „Chorus 2 soll mehr Bewegung haben“. Claude ändert nur show.yaml.
    • Oder den Effekt selbst in song.yaml vorgeben.
    • Timing: Takte, midi_offset oder bpm in song.yaml ändern.
    Danach wieder Schritt 9 bis 13. Jede Generierung wird als Version gesichert.
  15. Zurück zu einer älteren Fassungdu
    $PY tools/songgen.py such --versions
$PY tools/songgen.py such --restore 2026-10-03_1345
    Danach Schritt 11 und 12. Details in Abschnitt 9.
  16. In Git sicherndu
    git add songs/SuchAShame_v1 src/songs_generated.cpp src/songs_generated.h src/main.cpp
git commit -m "Song Such A Shame"
    Der Song-Ordner mit allen Versionen wird versioniert, nur MP3s und song.vorschlag.yaml nicht.

Die Struktur-Tabelle (quelle/struktur.xlsx)

Die Tabelle hat das Format deines Excel-Songkalkulators, ein Song pro Datei. Das Werkzeug liest nur die unten genannten Felder und erkennt sie an ihrer Beschriftung, nicht an der Position; alle anderen Spalten (ms, sekunden, millis akkum …) bleiben deine Kontrollrechnung und werden ignoriert. Millisekunden und Rundung übernimmt der Generator: er rechnet jede Part-Grenze aus der absoluten Zeit, dadurch entsteht keine Abweichung, die sich aufsummiert.

Feld im KopfPflichtBedeutung
Midi-StartNummer (A1, Wert in B1)jaDie Song-ID, 1..127, siehe Schritt 1.
Interpret (A2), Titel (A3)Titel jaOhne Beschriftung: die ersten beiden Texte in Spalte A, erst Interpret, dann Titel. Daraus wird der Lauftext „Titel by Interpret“.
BPM (Wert darunter)jaTempo des Songs.
StartTakt (Wert darunter)jaTaktnummer im DAW-Projekt, in der das Start-MIDI liegt.
StartBit (Wert daneben)nein (0)Wie weit das MIDI nach dem Taktanfang kommt, als Bruchteil des Takts: 0,125 → midi_offset: 1/8, 0,25 → 1/4, 0,375 → 3/8.
Audio (optional ergänzen)neinDateiname der MP3 in quelle/. Fehlt das Feld: die einzige MP3 im Ordner.

Ein Wert steht rechts neben seiner Beschriftung oder, wenn dort nichts steht, darunter.

Spalte pro PartPflichtBedeutung
SongpartjaName. Kommt er mehrfach vor, hängt das Werkzeug (2), (3) an.
bis taktjaTaktnummer im DAW, an der der Part endet (= Anfang des nächsten). Halbe Takte als Komma-Zahl, z. B. 2269,5. Der erste Part beginnt bei StartTakt + StartBit.
von taktNur Gegenprobe: passt der Wert nicht zum „bis takt“ der Zeile davor, warnt das Werkzeug. Gerechnet wird immer mit „bis takt“.
Energie 0-5neinwird energy.
Effektideeneinfrei formuliert („weißer Strobo auf den Auftakt“), wird idea. Claude setzt sie in der Show um.
Beschreibungneinwas musikalisch passiert, wird description.
BPMneinTempo dieses Parts. Wird nur übernommen, wenn es vom BPM im Kopf abweicht (Tempowechsel).
Akkorde (optional ergänzen)neinklingende Akkorde, z. B. Am F C G. Nur für den Bund-Marker-Vorschlag.

Schluss-Black: Heißt die letzte Zeile „BLACK“ (auch „fini“, „ende“), wird sie nicht als Part übernommen, denn nach dem letzten Part hängt der Generator selbst 10 s Schwarz an. Die Zeile braucht kein „bis takt“. Steht in „ms gerundet!!“ dieser Zeile ein anderer Wert als 10000, kommt er als end_black_ms in die song.yaml. Die „pause“ am Anfang bleibt ein normaler Part.

Deine song.yaml wird nie überschrieben. Gibt es sie schon, schreibt struktur2song.py sein Ergebnis als song.vorschlag.yaml daneben.

4 · sheet2song: Struktur aus Sheet + Audio (Alternative)

$PY tools/sheet2song.py <Song> --id <1..127> [Optionen]

<Song> ist der Ordner unter songs/. Sheet (.txt/.xml) und MP3 sucht das Tool im Ordner bzw. in quelle/. Von jeder Sorte darf dort genau eine Datei liegen.

Deine song.yaml wird nie überschrieben. Gibt es sie schon, schreibt das Tool sein Ergebnis als song.vorschlag.yaml daneben. Die Datei dient nur zum Vergleichen, der Generator beachtet sie nicht. Was du übernehmen willst, überträgst du von Hand.
Argument / OptionPflichtStandardBedeutung
<Song>jaOrdner unter songs/. Er muss schon existieren. Der Anfang des Namens genügt.
--id <n>jaSong-ID 1..127 = MIDI-Wert von CC 22 (0 ist der Pausen-Loop). Kollisionen prüft erst der Generator.
--bpm <zahl>neinaus dem SheetTempo. Nötig, wenn im Sheet weder <myTempo> noch <tempo> steht. Eine Angabe hier hat Vorrang vor dem Sheet, im Sheet hat myTempo Vorrang vor tempo.
--midi-offset <notenwert>nein1/8Wie spät das Start-MIDI nach Takt 1 kommt, z. B. 1/16, 3/8. Wird unverändert in song.yaml eingetragen.
--sheet <datei>neindie einzige .txt/.xml im Song-OrdnerSheet ausdrücklich angeben, z. B. wenn mehrere im Ordner liegen oder es woanders liegt.
--audio <datei>neindie einzige .mp3 im Song-OrdnerAudiodatei ausdrücklich angeben.

Gesucht wird im ganzen Song-Ordner außer in versionen/ und audio-analyse/. Das Tool schreibt genau eine Datei: song.yaml, oder song.vorschlag.yaml, wenn es song.yaml schon gibt.

Was aus dem Sheet gelesen wird

  • <title>, <artist>: Name und Lauftext auf der Scrollmatrix
  • <myTempo> (sonst <tempo>): BPM
  • <transpose>: Die Akkorde im Audio liegen um so viele Halbtöne höher. Beispiel ATTSS: Fm + 4 = Am.
  • <part name="…"> mit <row>: Part-Namen, erste Textzeile als lyrics, Akkorde als chords. Leere Parts (z. B. „Chorus Lines gelöscht“) werden übersprungen.
  • Taktzahl im Part-Namen: Endet der Name auf eine Taktangabe, z. B. Verse 1, 16 Takte oder drum Solo 2 takte, gilt diese Länge fest und der Part heißt danach nur verse 1. So zählen auch Parts ohne Akkorde (Synth-Intro, Drum-Solo). Je mehr Parts du so beschriftest, desto sicherer ist das Ergebnis.

Wie die Takte bestimmt werden

  1. Erwartete Länge aus dem Sheet:
    • eine Textzeile mit bis zu 2 Akkorden = 1 Takt, mit 3–4 Akkorden = 2 Takte;
    • eine Zeile mit mehreren Textzeilen = 1 Takt pro Textzeile;
    • eine reine Akkordzeile (Instrumental) = 1 Akkord pro Takt.
    Das ist nur eine Schätzung, denn Sheets notieren Wiederholungen oft nicht aus. sheet2song rechnet immer im 4/4-Takt mit einem Tempo. Takt- oder Tempowechsel trägst du danach von Hand in die Song-Datei ein.
  2. Beat-Raster: Das Tempo ist bekannt. Gesucht wird nur, wo die Schläge liegen, also der Versatz mit den stärksten Anschlägen auf dem Raster.
  3. Akkorde im Audio: Pro halbem Takt wird bestimmt, welcher der Sheet-Akkorde am besten klingt (Chroma-Analyse, siehe Abschnitt 10).
  4. Abgleich: Die Parts werden in Sheet-Reihenfolge so auf die Takte verteilt, dass die erwarteten Akkorde möglichst gut zum Audio passen (dynamische Programmierung). Grenzen liegen immer auf einem Taktanfang. Ein Part darf seine Akkordfolge wiederholen oder langsamer spielen (1 Akkord pro Takt oder pro 2 Takte). Parts mit Taktzahl im Namen bekommen genau diese Länge. Kleiner Malus, wenn die Länge stark von der Sheet-Schätzung abweicht: Das entscheidet bei Parts mit gleicher Akkordfolge (Chorus → Bridge).
  5. Takt-Eins: Alle 4 möglichen Zählzeiten werden als Taktanfang probiert. Die mit dem besten Abgleich gewinnt.
  6. Bund-Marker: Nur wenn der Song noch keine hat, kommt ein Vorschlag aus den Akkord-Grundtönen dazu (siehe Abschnitt 13).
  7. Pause und Ausklang: Stille Takte vor dem ersten Ton werden zum Part pause. Klingende Takte nach dem letzten Sheet-Part werden zu ende.

Die Ausgabe lesen

  part                     takte sheet  start mp3  akkorde
  intro                       12    10    0:02.81      67%
                           ! Pegelsprung vor Takt 5: -15.8 -> -3.7 dB
  verse 1                      9     9    0:36.30     100%
  …
  • takte: Ergebnis. sheet: Schätzung aus dem Sheet. Weichen beide ab, ist das oft richtig (ausgelassene Wiederholungen), sollte aber kurz geprüft werden.
  • start mp3: Position in der Audiodatei, zum Gegenhören.
  • akkorde: Anteil der halben Takte, in denen der erwartete Akkord erkannt wurde. Unter 50 % steht <- prüfen. Werte um 60–70 % sind bei Intros mit Effekten oder Sprechgesang normal.
  • ! Pegelsprung: Innerhalb des Parts ändert sich die Lautstärke um mindestens 3 dB. Das ist ein guter Kandidat, den Part für die Show zu teilen.

5 · Die Song-Datei song.yaml (gehört dir)

id: 31
name: "All The Things She Said"
artist: "t.A.T.u."
bpm: 86
beats_per_bar: 4
midi_offset: 3/8            # MIDI kommt drei Achtel nach Takt 1
audio: quelle/ATTSS.mp3        # relativ zum Song-Ordner

sections:
  - name: pause                 # eindeutig! Die Show-Datei verweist darauf
    bars: 1
  - name: intro
    bars: 4
    energy: 1                   # optional, deine Einschätzung 0-5
    lyrics: "All the things she said"
    description: "leiser Chant, am Ende Crescendo"
  - name: chorus 1
    bars: 8
    scene: SCENE_PINGPONG       # feste Vorgabe: hat Vorrang vor show.yaml
    scheme: SCHEME_RED
Diese Datei gehört dir. Hier stehen deine Ergänzungen zu Parts, Stimmungen und Effekten. Sie werden nie überschrieben:
  • Werkzeuge: songgen und songanalyze lesen die Datei nur. sheet2song schreibt sie nur, wenn es sie noch nicht gibt.
  • Claude: Ein Hook (tools/hook_protect_song.py, eingetragen in .claude/settings.json) blockiert jeden Schreibzugriff von Claude auf songs/…/song.yaml, dazu kommt eine Verbotsregel in denselben Einstellungen. Claude schlägt Änderungen im Chat vor, du trägst sie ein.
  • Restore: Auch beim Zurückholen einer alten Version bleibt deine aktuelle song.yaml unangetastet.
  • Kontrolle: In jeder Version steht die Prüfsumme der Datei. songgen.py ohne Argument zeigt, ob sie seit der letzten Generierung geändert wurde.

Einschätzung oder feste Vorgabe

Du schreibstWirkung
energy, description, mood, instruments, solo, lyricsEinschätzung. Claude leitet daraus die Show ab. Deine Angaben haben Vorrang vor den Messwerten der Analyse.
scene oder fxFeste Vorgabe. Gilt immer, egal was in show.yaml steht. Geräte-Overrides der Show für diesen Part entfallen dann.
scheme, fade, tail, devices, textFeste Vorgabe für Farbschema, Farbwanderung, Schluss-Akzent, einzelne Geräte bzw. Text auf der Matrix. Der Rest des Parts kommt weiter aus der Show.
Song-Ebene: scheme, scroll_text, scroll_title, scroll_delay, end_black_mshaben ebenfalls Vorrang vor show.yaml

Änderungswünsche als Anmerkung: Du kannst einen Wunsch einfach hinter den Wert schreiben, z. B. idea: "ruhig" -> zu statisch, hier fehlt eine langsame Verwandlung. Die Werkzeuge lesen den Rest der Zeile als Teil des Textes mit. Der Generator selbst wertet idea und die anderen Einschätzungen nicht aus: Sie wirken erst, wenn Claude die Show danach überarbeitet. Sag Claude deshalb, dass du Anmerkungen ergänzt hast. Die fertige Gestaltung steht danach in show.yaml; sie muss nicht in song.yaml zurückgetragen werden, und eine erledigte Anmerkung darf stehen bleiben.

Der Generator meldet jede übernommene Vorgabe in der Timeline als Hinweis, z. B. 'chorus 1': scene, scheme aus song.yaml (Vorrang vor show.yaml). Schreibweise der Felder wie in Abschnitt 7.

Alle Felder auf Song-Ebene

FeldPflichtStandardBedeutung

hard: true – springt im Takt zwischen den beiden Farben, statt weich überzublenden.
Weiß bleibt weiß. Ein tail übernimmt die Farbwanderung nicht, er kann ein eigenes fade haben.

Ohne eigenes scheme gilt das des Parts. Pro Part ist nur ein tail möglich. Für mehr Akzente den Part in song.yaml teilen.
textText auf den Matrix-Geräten, alle anderen Geräte spielen ihre Szene weiter. Position, Tempo und Farbe ergeben sich von selbst:
text: "FUN" – ein Wort, zentriert, pulsiert im Beat.
text: "THEY JUST WANNA HAVE FUN" – mehrere Wörter, pro Beat das nächste, danach von vorn.
text: {words: "HAVE FUN", per: bar} – per: beat (Standard), half (2 Beats), bar (ein Takt) oder eine Zahl in Beats.
text: {scroll: "I come home in the morning light"} – Lauftext, der genau am Part-Ende fertig ist (bei langen Parts mehrere Durchläufe).

Auf die SCROLLMATRIX passen 9 Zeichen pro Wort; ist ein Wort länger, läuft der ganze Text als Lauftext (der Generator weist darauf hin). Nur ASCII, also ae statt ä. Geht auch im tail. Nicht zusammen mit devices für die Matrix.

8 · Feste Regeln: Anfang & Ende

Diese Regeln setzt der Generator automatisch um, genau wie in den handgeschriebenen Songs:

MomentVerhalten
Start-MIDIDer erste Part ist auf allen Geräten progBlack. Eine Gestaltung dafür in der Show wird ignoriert, mit Hinweis.
LauftextSCROLLMATRIX (und GITBOARD) zeigt „Titel by Interpret“. Abschalten oder ändern mit scroll_text, scroll_title, scroll_delay. Ein Durchlauf dauert (MATRIX_WIDTH − 2 + 6 × Zeichen) × delay ms, die Breite liest der Generator aus definitions.h.
Wiedereinstieg
Variante 1		Endet der Text höchstens 4 s vor einer Part-Grenze, bleibt die Matrix erst schwarz. Der Text endet dann genau an der Grenze (wie im Original von „Dancing On My Own“).
Wiedereinstieg
Variante 2		Sonst läuft der Text sofort. Danach zeigt die Matrix den Rest des laufenden Parts verkürzt und steigt an der nächsten Grenze ein. Der Rest beginnt auf einem Beat, damit Szenen, die im Takt blinken, nicht versetzt laufen.
EndeNach dem letzten Part 10 s (end_black_ms) progBlack auf allen Geräten, dann clearAll(); switchToSong(0); (Pausen-Loop).

Was in der Firmware landet

In der Firmware ist jeder Song, dessen Ordner eine generated.cpp enthält. song.yaml und show.yaml zu löschen ändert daran nichts, der Code bleibt eingefroren erhalten. Einen Song entfernen: den Ordner (oder nur seine generated.cpp) löschen und danach $PY tools/songgen.py --assemble ausführen.

So werden die Millisekunden berechnet

  • Dauer eines Beats = 60000 / BPM ms, ein Takt = 4 Beats. Bei 86 BPM: 697,67 ms bzw. 2790,7 ms.
  • Zuerst werden die absoluten Startzeiten aller Parts ab Takt 1 berechnet und erst dann gerundet: Dauer = round(Ende) − round(Start). So entsteht keine Rundungsdrift wie beim Aufaddieren einzelner gerundeter Dauern. Der Abgleich mit dem handgeschriebenen „Dancing On My Own“ ergab 1 ms Abweichung nach 4:25 min.
  • Zeitbasis im Code ist das Start-MIDI: Alle Zeiten werden um midi_offset verschoben. Bei 1/8 und 86 BPM ist der erste Part 349 ms kürzer.
  • Die case-Nummern laufen in 5er-Schritten. case 1 und 2 sind für den Lauftext der Scrollmatrix reserviert.
  • Kein Versatz zum Klick über den Song: Ein Gerät bemerkt eine Part-Grenze erst einige Millisekunden später (ein Schleifendurchlauf mit FastLED.show()). Früher ging diese Verspätung bei jedem Wechsel verloren und summierte sich über viele Parts, deshalb wurden Parts in den alten Songs von Hand verkürzt. Bei generierten Songs nimmt die Firmware die Verspätung jetzt in den nächsten Part mit (isGeneratedSong(), wird vom Generator gepflegt). Parts also nie mehr künstlich verkürzen, die Taktzahlen aus dem DAW gelten exakt. Die alten handgeschriebenen Songs laufen unverändert.
  • Die Beat-Effekte (Blitze auf die Viertel, PingPong, Lampen-Puls) rechnen den Beat exakt aus dem BPM, nicht aus einer auf ganze Millisekunden gerundeten Beat-Länge.

10 · Wie die MP3 analysiert wird

Kurz gesagt: Die MP3 wird ausschließlich lokal analysiert, mit der Python-Bibliothek librosa in tools/.venv. Sie wird als Mono-Signal geladen und in Fenster von etwa 23 ms zerlegt. Daraus werden berechnet:

  • Chroma: die Energie der 12 Halbtöne, auf dem harmonischen Anteil ohne Schlagzeug. Daraus kommen Akkorde und Tonart.
  • Onsets und Kick-Energie unter 120 Hz: Daraus kommen die Lage des Beat-Rasters und die Takt-Eins. Das Tempo selbst kommt von dir.
  • RMS-Pegel: für Power, Stille, Pegelsprünge und Stopps.
  • Spektralschwerpunkt und Bassanteil: für Helligkeit und Lowend.
  • Formwechsel: Wo sich Klangfarbe, Harmonie und Pegel ändern, liegen Part-Grenzen. Damit wird die Struktur geprüft.

Wie sheet2song daraus die Takte bestimmt:

  1. Es rechnet die Sheet-Akkorde um den <transpose>-Wert hoch.
  2. Pro halbem Takt bestimmt es, welcher dieser Akkorde im Audio am besten klingt.
  3. Dann verteilt es die Parts in Sheet-Reihenfolge auf die Takte, sodass die Akkordfolgen bestmöglich passen. Ein Part darf seine Akkorde wiederholen oder halb so schnell spielen. Die Sheet-Länge entscheidet nur bei Mehrdeutigkeit, etwa wenn Chorus und Bridge dieselben Akkorde haben.

Weil nur die Akkorde aus deinem Sheet in Frage kommen, ist das deutlich zuverlässiger als eine freie Akkorderkennung. Die Details stehen in den Tabellen und Abschnitten darunter.

Beide Werkzeuge nutzen die Python-Bibliothek librosa. Alles läuft lokal, kein Cloud-Dienst. Die MP3 wird als Mono-Signal mit 22 050 Hz geladen und in kurze Fenster zerlegt (512 Samples ≈ 23 ms).

Akkorderkennung

Für jeden halben Takt wird der mittlere Chroma-Vektor mit den Dreiklang-Schablonen der Sheet-Akkorde verglichen (Kosinus-Ähnlichkeit). Septimen und Slash-Akkorde werden dabei auf Dur/Moll-Dreiklänge reduziert. Weil nur die Akkorde aus dem Sheet in Frage kommen, ist das viel zuverlässiger als eine freie Akkorderkennung.

Grenzen des Verfahrens

  • Das Tempo wird nicht erkannt, es kommt immer von dir. Automatische Beat-Tracker liegen gern daneben: Bei ATTSS meldete der Standard-Tracker 117 statt 86 BPM, ChatGPT 86,76 BPM. Das wären nach gut 3 Minuten fast 2 s Versatz.
  • Parts mit identischer Akkordfolge direkt hintereinander, etwa Chorus → Bridge bei ATTSS, sind nur über die Sheet-Länge unterscheidbar. Deshalb sollte das Sheet vollständig sein.
  • Sprechgesang, stark effektierte Intros oder Parts ohne Harmonie (nur Drums) erkennt die Akkordanalyse schlecht. Das zeigt die Spalte „akkorde“.
  • Stimmung und Energie sind Messwerte, keine Musikalität. Deine description/energy haben bei der Gestaltung Vorrang.

13 · Bund-Marker-LEDs

Grundregel: Marker, die du gesetzt oder akzeptiert hast, werden nie mehr verändert. Das gilt für jedes Werkzeug und für Claude. Vorgeschlagen wird nur für Songs, die noch gar keine Marker haben.

Wie der Vorschlag entsteht

  • Grundtöne aller Akkorde im Song, nach dem Transpose, z. B. Sheet C# + 4 = F.
  • Jeder Grundton wird auf der E-Saite und auf der A-Saite markiert. Beide Saiten teilen sich eine LED pro Bund: ESaite_C und ASaite_F sind dieselbe LED am 8. Bund.
  • Keine Marker auf dem 5. und 12. Bund (dort leuchten immer die blauen LEDs) und keine auf der Leersaite.
  • Höchstens 7 Marker (markerLED1…7). Bei mehr fallen die seltensten Akkorde weg, mit Hinweis.
  • Das Mapping auf die LEDs von Gitarre und Bass passiert wie bisher über die Defines in definitions.h.

Wo die Marker stehen

FallVerhalten
Song-ID hat einen case in src/markerLEDs.cppDeine Handarbeit gilt immer. sheet2song schlägt nichts vor, der Generator erzeugt keine Grund-Marker. Marker-Listen in song.yaml werden dann ignoriert, Slot-Angaben für einzelne Parts gelten trotzdem. Das betrifft z. B. #31 ATTSS.
Neuer Song ohne Markersheet2song schreibt einen markers:-Block als Vorschlag ans Ende der Song-Datei. Behältst oder änderst du ihn, gilt er als deiner.
Song-Datei hat schon markers:Die Datei wird ohnehin nicht mehr geschrieben. In den Vorschlag (song.vorschlag.yaml) übernimmt sheet2song den Block Zeichen für Zeichen, der Generator setzt ihn nur um.
markers:
  all: [ESaite_F, ASaite_C, ASaite_E, ASaite_F]   # Gitarre und Bass
  bass: [ESaite_F, ESaite_G]                     # nur Bass (ersetzt all)
  parts:                                        # Spezial-Marker für einzelne Abschnitte
    solo: {bass: [ESaite_Cis, ESaite_Dis]}       # gilt im Abschnitt inkl. seines Tails

Einzelne Marker in einzelnen Parts (Slot-Angabe)

Soll in einem Part nur ein zusätzlicher Marker an- oder ausgehen, schreibst du statt einer Liste {Slot: Marker}. Der Slot ist die Nummer von markerLED1…7, 0 als Marker schaltet den Slot aus.

markers:
  parts:
    chorus 2 hit: {bass: {5: ASaite_E}}     # markerLED5 nur beim Bass, nur in diesem Part
    bridge 1:     {bass: {5: ASaite_E}}
  • Das funktioniert auch bei Songs mit handgeschriebenen Grund-Markern in markerLEDs.cpp. So werden die Marker übernommen, die ein alter Song mitten im Code gesetzt hat.
  • Der Generator schreibt daraus Code an den Anfang der Song-Funktion. Er läuft in jedem Durchlauf nach setMarkerLEDs(), genau wie früher die Zeilen im handgeschriebenen Song.
  • Außerhalb der genannten Parts gelten wieder die Grund-Marker. Belegen die Grund-Marker den Slot nicht, wird er dort ausgeschaltet.
  • Schlüssel wie bei den Listen: all, guitar, bass. Ein Part mit tail schließt den Tail ein.

Der Generator erzeugt aus den Listen setGeneratedMarkerLEDs() in songs_generated.cpp. Aufgerufen wird sie im default-Zweig von setMarkerLEDs(), also nur, wenn es keinen handgeschriebenen case gibt. Ungültige Marker-Namen, mehr als 7 Marker oder unbekannte Abschnitte meldet er als Fehler.

Wie der Schutz abgesichert ist

  • In den Werkzeugen (tools/markers.py): Ein handgeschriebener case in setMarkerLEDs() hat immer Vorrang. sheet2song schreibt eine vorhandene song.yaml nie und übernimmt deren markers:-Block wörtlich in den Vorschlag. Die Show-Datei darf keine Marker enthalten, sonst bricht der Generator ab.
  • Bei Claude: Die Regel „nie ändern, was gesetzt oder akzeptiert ist“ steht im Memory und im Skill new-song. Fällt Claude etwas auf, etwa ein fehlender Akkord-Grundton, gibt es nur einen Hinweis im Chat, keine Änderung.

Änderungen am bestehenden Code

In src/markerLEDs.cpp sind genau zwei Dinge dazugekommen. Die handgeschriebenen cases sind unverändert.

#include "songs_generated.h"	// setGeneratedMarkerLEDs()
…
		default://defaultLoop();
			// kein handgeschriebener case -> Marker der generierten Songs (songs/*.yaml, sonst nichts)
			setGeneratedMarkerLEDs(songID, partID);
			break;

Vorher stand im default-Zweig nur „DO NOTHING“. Für Songs ohne handgeschriebenen case und ohne markers: in der YAML bleibt es dabei: Die generierte Funktion setzt dann nichts.

Im generierten Code werden bei jedem Aufruf alle 7 Marker gesetzt, unbenutzte auf 0. So bleiben beim Wechsel in einen Part mit Spezial-Markern keine alten Marker stehen. Unterschiedliche Marker für Gitarre und Bass landen in #ifdef GIT … #else … #endif.

Geprüft

  • Vorschlag für eine neue Song-ID aus dem ATTSS-Sheet erzeugt: 5 Marker, siehe Vergleich unten.
  • Für #31 (handgeschrieben) kommt kein Vorschlag, und der Generator meldet „von Hand in markerLEDs.cpp“.
  • markers:-Block wie ein User geändert (andere Marker plus Spezial-Marker im Solo), dann sheet2song erneut (damals noch mit --force): Der Block blieb Zeichen für Zeichen gleich.
  • Testsong mit Spezial-Markern nur für den Bass im Solo: Der erzeugte Code setzt im Solo für den Bass die Spezial-Marker, für die Gitarre die normalen. Er baut für Gitarre, Bass und Lampe.
