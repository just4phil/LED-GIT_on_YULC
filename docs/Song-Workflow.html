Song-Workflow: vom Chord-Sheet zur LED-Show

Neue Songs werden nicht mehr von Hand in songs.cpp programmiert: Sheet + MP3 → Struktur in Takten → Show-Dramaturgie → generierter C++-Code. Stand 28.09.2026.

1 · Überblick

Ein Song läuft ab dem Start-MIDI-Signal (CC 22 = Song-ID, Kanal 10) millisekundengenau durch. Alle Part-Dauern ergeben sich deshalb aus Tempo × Takten. Das Werkzeug rechnet sie aus, statt sie per Excel zu ermitteln.

DateiWerInhalt
songs/<name>.yamldu (vom Tool vorbereitet)Was musikalisch passiert: Tempo, Takte je Part, MIDI-Offset, Lyrics, Akkorde, Beschreibung
songs/<name>.show.yamlClaudeWie es aussieht: Szene, Farbschema, Geräte-Overrides, Akzente je Part (per Part-Name, ohne Takte)
src/songs_generated.cpp/.hGeneratorC++-Funktion pro Song, nie von Hand ändern

2 · Einmalige Einrichtung

Die Python-Werkzeuge laufen in einer eigenen Umgebung tools/.venv (nicht versioniert). Einmal pro Rechner, in Git Bash im Projektordner:

python -m venv tools/.venv
tools/.venv/Scripts/python -m pip install -r tools/requirements.txt

Pakete: librosa (Audioanalyse), numpy, matplotlib (Analysebild), soundfile, pyyaml. Getestet mit Python 3.9.

Tipp: Die Konsolenausgabe enthält Umlaute. Falls Zeichensalat erscheint, vor die Befehle PYTHONIOENCODING=utf-8 setzen. Warnungen von librosa blendet PYTHONWARNINGS=ignore aus.

3 · Neuer Song Schritt für Schritt

  1. MP3 ablegendu
    Datei nach songs/audio/ kopieren. Der Ordner wird nicht versioniert. Wichtig: Es muss genau die Version sein, die live läuft, mit demselben Tempo und derselben Stille am Anfang.
  2. Struktur erzeugensheet2song
    tools/.venv/Scripts/python tools/sheet2song.py "C:/…/Songtitel.txt" songs/audio/SONG.mp3 --id 32
    Das Tool liest Sheet und Audio und schreibt songs/<titel>.yaml. Details in Abschnitt 4.
  3. Struktur prüfendu
    Tabelle in der Konsole ansehen: Passen die Taktzahlen? Alle Parts mit <- prüfen oder # !-Hinweis kurz gegenhören. midi_offset prüfen. Parts mit großem Pegelsprung eventuell aufteilen, z. B. verse 2a/verse 2b. Optional description/energy ergänzen: Deine Einschätzung hat bei der Gestaltung Vorrang vor den Messwerten.
  4. Show gestalten lassenClaude
    In Claude Code z. B.: „Gestalte die Show für songs/<titel>.yaml“. Claude nutzt den Skill new-song und geht so vor:
    • Analyse laufen lassen und das Analysebild ansehen,
    • <titel>.show.yaml schreiben,
    • generieren und alle ESP32-Geräte bauen,
    • dir die Timeline zeigen.
  5. Flashen & testendu
    pio run -e esp32-s3-devkitc-1 --target upload pro Gerät (Gerät in src/definitions.h wählen). Song per MIDI starten: CC 22 = Song-ID auf Kanal 10.
  6. Nachsteuerndu Claude
    Gefällt ein Part nicht, genügt ein Satz wie „Chorus 2 soll mehr Bewegung haben“. Geändert wird nur die Show-Datei, danach wird neu generiert. Stimmt ein Timing nicht, wird die Song-Datei korrigiert (Takte, Offset).

4 · sheet2song: Struktur aus Sheet + Audio

tools/.venv/Scripts/python tools/sheet2song.py <sheet.txt> <audio.mp3> --id <0..127> [Optionen]
OptionBedeutung
--idSong-ID = MIDI-Wert von CC 22 (Pflicht). Der Generator meldet, wenn die ID in main.cpp schon vergeben ist.
--bpmTempo, nur nötig, wenn im Sheet weder <myTempo> noch <tempo> steht. myTempo hat Vorrang.
--midi-offsetNotenwert, wie spät das Start-MIDI nach Takt 1 kommt (Standard 1/8)
--outandere Zieldatei (Standard songs/<titel>.yaml)
--forcevorhandene Datei überschreiben. Ohne diese Option bricht das Tool ab, damit deine Änderungen nicht verloren gehen.

Was aus dem Sheet gelesen wird

  • <title>, <artist>: Name und Lauftext auf der Scrollmatrix
  • <myTempo> (sonst <tempo>): BPM
  • <transpose>: Die Akkorde im Audio liegen um so viele Halbtöne höher. Beispiel ATTSS: Fm + 4 = Am.
  • <part name="…"> mit <row>: Part-Namen, erste Textzeile als lyrics, Akkorde als chords. Leere Parts (z. B. „Chorus Lines gelöscht“) werden übersprungen.

Wie die Takte bestimmt werden

  1. Erwartete Länge aus dem Sheet:
    • eine Textzeile mit bis zu 2 Akkorden = 1 Takt, mit 3–4 Akkorden = 2 Takte;
    • eine Zeile mit mehreren Textzeilen = 1 Takt pro Textzeile;
    • eine reine Akkordzeile (Instrumental) = 1 Akkord pro Takt.
    Das ist nur eine Schätzung, denn Sheets notieren Wiederholungen oft nicht aus.
  2. Beat-Raster: Das Tempo ist bekannt. Gesucht wird nur, wo die Schläge liegen, also der Versatz mit den stärksten Anschlägen auf dem Raster.
  3. Akkorde im Audio: Pro halbem Takt wird bestimmt, welcher der Sheet-Akkorde am besten klingt (Chroma-Analyse, siehe Abschnitt 10).
  4. Abgleich: Die Parts werden in Sheet-Reihenfolge so auf die Takte verteilt, dass die erwarteten Akkorde möglichst gut zum Audio passen (dynamische Programmierung). Grenzen liegen immer auf einem Taktanfang. Ein Part darf seine Akkordfolge wiederholen oder halb so schnell spielen. Kleiner Malus, wenn die Länge stark von der Sheet-Schätzung abweicht: Das entscheidet bei Parts mit gleicher Akkordfolge (Chorus → Bridge).
  5. Takt-Eins: Alle 4 möglichen Zählzeiten werden als Taktanfang probiert. Die mit dem besten Abgleich gewinnt.
  6. Bund-Marker: Nur wenn der Song noch keine hat, kommt ein Vorschlag aus den Akkord-Grundtönen dazu (siehe Abschnitt 13).
  7. Pause und Ausklang: Stille Takte vor dem ersten Ton werden zum Part pause. Klingende Takte nach dem letzten Sheet-Part werden zu ende.

Die Ausgabe lesen

  part                     takte sheet  start mp3  akkorde
  intro                       12    10    0:02.81      67%
                           ! Pegelsprung vor Takt 5: -15.8 -> -3.7 dB
  verse 1                      9     9    0:36.30     100%
  …
  • takte: Ergebnis. sheet: Schätzung aus dem Sheet. Weichen beide ab, ist das oft richtig (ausgelassene Wiederholungen), sollte aber kurz geprüft werden.
  • start mp3: Position in der Audiodatei, zum Gegenhören.
  • akkorde: Anteil der halben Takte, in denen der erwartete Akkord erkannt wurde. Unter 50 % steht <- prüfen. Werte um 60–70 % sind bei Intros mit Effekten oder Sprechgesang normal.
  • ! Pegelsprung: Innerhalb des Parts ändert sich die Lautstärke um mindestens 3 dB. Das ist ein guter Kandidat, den Part für die Show zu teilen.

sections:
  - name: pause                 # eindeutig! Die Show-Datei verweist darauf

  - name: intro
    bars: 4
    energy: 1                   # optional, deine Einschätzung 0-5
    lyrics: "All the things she said"

FeldBedeutung

midi_offsetNotenwert (1/8, 1/16, 3/16, negativ = MIDI kommt vor Takt 1). Der erste Part wird entsprechend kürzer, alles andere bleibt auf dem Raster. Nur im Notfall midi_offset_ms.

energy, lyrics, chords, instruments, solo, mood, descriptionfrei. Das ist Futter für die Gestaltung. energy ist zugleich die Rückfalllösung, wenn ein Part in der Show fehlt (0 Black, 1 Calm, 2 Verse, 3 Buildup, 4–5 Drop).

7 · Die Show-Datei (technisch)

function: gen_AllTheThingsSheSaid
scheme: SCHEME_ICE                  # Grundfarben
sections:
  intro:                            # = name aus der Song-Datei
    scene: SCENE_CALM
    scheme: SCHEME_ICE
    tail:                           # letzte 2 Beats als eigener Part
      beats: 2
      scene: SCENE_BUILDUP
    why: "leiser Chant, Crescendo in den Band-Einsatz"
  verse 1b:
    scene: SCENE_VERSE
    devices:                        # Ausnahmen für einzelne Geräte
      ANDRESGIT: "progSymmetricVU(${dur}, ${next}, ${bpm})"
  bridge hit:
    fx: "progStrobo(${dur}, ${next}, 75, CRGB::White)"
FeldBedeutung
sceneSzene für alle Geräte, jedes zeigt sie auf seine Art (siehe docs/LED-Effekte-und-Szenen.html): SCENE_CALM, _VERSE, _BUILDUP, _DROP, _FIRE, _WAVE_LR, _WAVE_RL, _WAVE_OUT, _PINGPONG, _SOLO_GIT, _SOLO_BASS, _SOLO_DRUMS
fxbeliebiger Effektaufruf für alle Geräte, statt einer Szene
schemeFarbschema: SCHEME_FIRE, _ICE, _NEON, _ROYAL, _TOXIC, _SUNSET, _RETRO, _WHITE, _RED, _BLUE, _RANDOM
devicesAusnahmen: guitar, lamp, matrix oder einzelne Geräte ANDRESGIT, RINASBASS, LAMPE1, LAMPE2, SCROLLMATRIX. Ein einzelnes Gerät hat Vorrang vor seiner Klasse.
taildie letzten N Beats als eigener Part (Strobo-Absprung, Aufladen vor dem Chorus)
whyBegründung, landet als Kommentar im C++-Code
Platzhalter${dur} Part-Dauer, ${next} nächster Part, ${bpm}, ${beat}, ${half}, ${bar} in ms
Song-Ebenefunction, scheme, scroll_text (false = kein Lauftext), scroll_title, scroll_delay (Standard 90), end_black_ms (Standard 10000)
In der Show-Datei stehen keine Takte oder Tempi. Der Generator bricht ab, wenn doch, oder wenn ein Part-Name nicht in der Song-Datei vorkommt. So kann die Show nicht unbemerkt von der Struktur abweichen.

8 · Feste Regeln: Anfang & Ende

Diese Regeln setzt der Generator automatisch um, genau wie in den handgeschriebenen Songs:

MomentVerhalten
Start-MIDIDer erste Part ist auf allen Geräten progBlack. Eine Gestaltung dafür in der Show wird ignoriert, mit Hinweis.
LauftextSCROLLMATRIX zeigt „Titel by Interpret“. Ein Durchlauf dauert (MATRIX_WIDTH − 2 + 6 × Zeichen) × delay ms, die Breite liest der Generator aus definitions.h.
Wiedereinstieg
Variante 1		Endet der Text höchstens 4 s vor einer Part-Grenze, bleibt die Matrix erst schwarz. Der Text endet dann genau an der Grenze (wie im Original von „Dancing On My Own“).
Wiedereinstieg
Variante 2		Sonst läuft der Text sofort. Danach zeigt die Matrix den Rest des laufenden Parts verkürzt und steigt an der nächsten Grenze ein. Der Rest beginnt auf einem Beat, damit Szenen, die im Takt blinken, nicht versetzt laufen.
EndeNach dem letzten Part 10 s progBlack auf allen Geräten, dann clearAll(); switchToSong(0); (Pausen-Loop).

9 · Generator & Timing

tools/.venv/Scripts/python tools/songgen.py --dry-run   # nur Timeline zeigen
tools/.venv/Scripts/python tools/songgen.py             # alle songs/*.yaml → C++
pio run -e esp32-s3-devkitc-1

Der Generator verarbeitet immer alle Songs. Er schreibt src/songs_generated.cpp/.h neu und trägt die Songs in main.cpp zwischen den Markern GENERATED SONGS ein. Handgeschriebene Songs in songs.cpp bleiben unberührt.

So werden die Millisekunden berechnet

  • Dauer eines Beats = 60000 / BPM ms, ein Takt = 4 Beats. Bei 86 BPM: 697,67 ms bzw. 2790,7 ms.
  • Zuerst werden die absoluten Startzeiten aller Parts ab Takt 1 berechnet und erst dann gerundet: Dauer = round(Ende) − round(Start). So entsteht keine Rundungsdrift wie beim Aufaddieren einzelner gerundeter Dauern. Der Abgleich mit dem handgeschriebenen „Dancing On My Own“ ergab 1 ms Abweichung nach 4:25 min.
  • Zeitbasis im Code ist das Start-MIDI: Alle Zeiten werden um midi_offset verschoben. Bei 1/8 und 86 BPM ist der erste Part 349 ms kürzer.
  • Die case-Nummern laufen in 5er-Schritten. case 1 und 2 sind für den Lauftext der Scrollmatrix reserviert.

10 · Wie die MP3 analysiert wird

Kurz gesagt: Die MP3 wird ausschließlich lokal analysiert, mit der Python-Bibliothek librosa in tools/.venv. Sie wird als Mono-Signal geladen und in Fenster von etwa 23 ms zerlegt. Daraus werden berechnet:

  • Chroma: die Energie der 12 Halbtöne, auf dem harmonischen Anteil ohne Schlagzeug. Daraus kommen Akkorde und Tonart.
  • Onsets und Kick-Energie unter 120 Hz: Daraus kommen die Lage des Beat-Rasters und die Takt-Eins. Das Tempo selbst kommt von dir.
  • RMS-Pegel: für Power, Stille, Pegelsprünge und Stopps.
  • Spektralschwerpunkt und Bassanteil: für Helligkeit und Lowend.
  • Formwechsel: Wo sich Klangfarbe, Harmonie und Pegel ändern, liegen Part-Grenzen. Damit wird die Struktur geprüft.

Wie sheet2song daraus die Takte bestimmt:

  1. Es rechnet die Sheet-Akkorde um den <transpose>-Wert hoch.
  2. Pro halbem Takt bestimmt es, welcher dieser Akkorde im Audio am besten klingt.
  3. Dann verteilt es die Parts in Sheet-Reihenfolge auf die Takte, sodass die Akkordfolgen bestmöglich passen. Ein Part darf seine Akkorde wiederholen oder halb so schnell spielen. Die Sheet-Länge entscheidet nur bei Mehrdeutigkeit, etwa wenn Chorus und Bridge dieselben Akkorde haben.

Weil nur die Akkorde aus deinem Sheet in Frage kommen, ist das deutlich zuverlässiger als eine freie Akkorderkennung. Die Details stehen in den Tabellen und Abschnitten darunter.

Beide Werkzeuge nutzen die Python-Bibliothek librosa. Alles läuft lokal, kein Cloud-Dienst. Die MP3 wird als Mono-Signal mit 22 050 Hz geladen und in kurze Fenster zerlegt (512 Samples ≈ 23 ms).

Akkorderkennung

Für jeden halben Takt wird der mittlere Chroma-Vektor mit den Dreiklang-Schablonen der Sheet-Akkorde verglichen (Kosinus-Ähnlichkeit). Septimen und Slash-Akkorde werden dabei auf Dur/Moll-Dreiklänge reduziert. Weil nur die Akkorde aus dem Sheet in Frage kommen, ist das viel zuverlässiger als eine freie Akkorderkennung.

Grenzen des Verfahrens

  • Das Tempo wird nicht erkannt, es kommt immer von dir. Automatische Beat-Tracker liegen gern daneben: Bei ATTSS meldete der Standard-Tracker 117 statt 86 BPM, ChatGPT 86,76 BPM. Das wären nach gut 3 Minuten fast 2 s Versatz.
  • Parts mit identischer Akkordfolge direkt hintereinander, etwa Chorus → Bridge bei ATTSS, sind nur über die Sheet-Länge unterscheidbar. Deshalb sollte das Sheet vollständig sein.
  • Sprechgesang, stark effektierte Intros oder Parts ohne Harmonie (nur Drums) erkennt die Akkordanalyse schlecht. Das zeigt die Spalte „akkorde“.
  • Stimmung und Energie sind Messwerte, keine Musikalität. Deine description/energy haben bei der Gestaltung Vorrang.

13 · Bund-Marker-LEDs

Grundregel: Marker, die du gesetzt oder akzeptiert hast, werden nie mehr verändert. Das gilt für jedes Werkzeug und für Claude. Vorgeschlagen wird nur für Songs, die noch gar keine Marker haben.

Wie der Vorschlag entsteht

  • Grundtöne aller Akkorde im Song, nach dem Transpose, z. B. Sheet C# + 4 = F.
  • Jeder Grundton wird auf der E-Saite und auf der A-Saite markiert. Beide Saiten teilen sich eine LED pro Bund: ESaite_C und ASaite_F sind dieselbe LED am 8. Bund.
  • Keine Marker auf dem 5. und 12. Bund (dort leuchten immer die blauen LEDs) und keine auf der Leersaite.
  • Höchstens 7 Marker (markerLED1…7). Bei mehr fallen die seltensten Akkorde weg, mit Hinweis.
  • Das Mapping auf die LEDs von Gitarre und Bass passiert wie bisher über die Defines in definitions.h.

Wo die Marker stehen

FallVerhalten
Song-ID hat einen case in src/markerLEDs.cppDeine Handarbeit gilt immer. sheet2song schlägt nichts vor, der Generator erzeugt nichts. Das betrifft z. B. #31 ATTSS.
Neuer Song ohne Markersheet2song schreibt einen markers:-Block als Vorschlag ans Ende der Song-Datei. Behältst oder änderst du ihn, gilt er als deiner.
Song-Datei hat schon markers:sheet2song --force übernimmt den Block Zeichen für Zeichen, der Generator setzt ihn nur um.
markers:
  all: [ESaite_F, ASaite_C, ASaite_E, ASaite_F]   # Gitarre und Bass
  bass: [ESaite_F, ESaite_G]                     # nur Bass (ersetzt all)
  parts:                                        # Spezial-Marker für einzelne Abschnitte
    solo: {bass: [ESaite_Cis, ESaite_Dis]}       # gilt im Abschnitt inkl. seines Tails

Der Generator erzeugt daraus setGeneratedMarkerLEDs() in songs_generated.cpp. Aufgerufen wird sie im default-Zweig von setMarkerLEDs(), also nur, wenn es keinen handgeschriebenen case gibt. Ungültige Marker-Namen, mehr als 7 Marker oder unbekannte Abschnitte meldet er als Fehler.

Wie der Schutz abgesichert ist

  • In den Werkzeugen (tools/markers.py): Ein handgeschriebener case in setMarkerLEDs() hat immer Vorrang. sheet2song übernimmt einen vorhandenen markers:-Block wörtlich. Die Show-Datei darf keine Marker enthalten, sonst bricht der Generator ab.
  • Bei Claude: Die Regel „nie ändern, was gesetzt oder akzeptiert ist“ steht im Memory und im Skill new-song. Fällt Claude etwas auf, etwa ein fehlender Akkord-Grundton, gibt es nur einen Hinweis im Chat, keine Änderung.

Änderungen am bestehenden Code

In src/markerLEDs.cpp sind genau zwei Dinge dazugekommen. Die handgeschriebenen cases sind unverändert.

#include "songs_generated.h"	// setGeneratedMarkerLEDs()
…
		default://defaultLoop();
			// kein handgeschriebener case -> Marker der generierten Songs (songs/*.yaml, sonst nichts)
			setGeneratedMarkerLEDs(songID, partID);
			break;

Vorher stand im default-Zweig nur „DO NOTHING“. Für Songs ohne handgeschriebenen case und ohne markers: in der YAML bleibt es dabei: Die generierte Funktion setzt dann nichts.

Im generierten Code werden bei jedem Aufruf alle 7 Marker gesetzt, unbenutzte auf 0. So bleiben beim Wechsel in einen Part mit Spezial-Markern keine alten Marker stehen. Unterschiedliche Marker für Gitarre und Bass landen in #ifdef GIT … #else … #endif.

Geprüft

  • Vorschlag für eine neue Song-ID aus dem ATTSS-Sheet erzeugt: 5 Marker, siehe Vergleich unten.
  • Für #31 (handgeschrieben) kommt kein Vorschlag, und der Generator meldet „von Hand in markerLEDs.cpp“.
  • markers:-Block wie ein User geändert (andere Marker plus Spezial-Marker im Solo), dann sheet2song --force: Der Block blieb Zeichen für Zeichen gleich.
  • Testsong mit Spezial-Markern nur für den Bass im Solo: Der erzeugte Code setzt im Solo für den Bass die Spezial-Marker, für die Gitarre die normalen. Er baut für Gitarre, Bass und Lampe.
