1Kontext & Anwendungsfall

Derzeit wird das Zielgerät über genau ein #define in src/definitions.h (Zeile 46 ff.) zur Compile-Zeit festgelegt. GITBOARD lief bisher auf einem Teensy 4.0, ANDRESGIT auf einem ESP32-S3.

Neues Ziel: ein ESP32-Controller (dieselbe BLE- und Rotary-Encoder-Hardware) soll wahlweise zwei verschiedene LED-Konfigurationen ansteuern:

AspektANDRESGIT (Gitarre)GITBOARD (Board)
LED-Anzahlanz_LEDs_GIT1 = 163anz_LEDs_GITBOARD = 278
Fret-Markerja (rot/blau, GITMARKER_GIT1)nein (NOMARKER)
Blinding-LEDs ausja (Fretboard-Bereich geschwärzt)nein
Matrix-Remapeingebaute Zigzag-AnordnungSpezial-myRemapFn()
Ausgabe-Kanäleleds1 (Fretboard+Marker), leds2 (Strap)volles Bild über einen Kanal
Text-/Scroll-Effektenicht genutztgenutzt (eigene Cursor-Positionen)

Praktischer Ablauf: Controller von einer Gitarre abziehen → an die andere LED-Konfiguration anstecken → per Rotary-Encoder-Geste zur Laufzeit umschalten, ohne neu zu flashen. MIDI-In und BLE-Proxy bleiben in beiden Modi identisch aktiv (gleiche Hardware) — nur das LED-Rendering ändert sich.

2Ausgangslage — warum das gut machbar ist

Die Architektur ist bereits weitgehend laufzeitfähig.
  • LEDGITBOARD ist schon eine normale boolean-Variable (main.cpp:61/64) und steuert bereits ~70 Verzweigungen in songs.cpp sowie Verzweigungen in FXprograms.cpp und matrixFunctions.cpp (if (LEDGITBOARD) { … }).
  • Festgenagelt wird der Modus nur durch (a) die Compile-Zeit-Initialisierung dieser Variable und (b) einige wenige verbliebene #ifdef-Blöcke.
  • Da GITBOARD künftig ebenfalls auf ESP32 läuft, entfällt das schwierige Teensy↔ESP32-Plattformproblem (andere Pins, andere Timer, anderes MIDI-Serial, kein BLE) komplett.
  • Die CRGB-Puffer leds/leds1/leds2 sind bereits mit NUMMATRIX (= 22×23 = 506, also > 278) dimensioniert (main.cpp:69-71) → kein Reallokieren; beide Konfigurationen passen in dieselben Puffer.

3Getroffene Design-Entscheidungen

FrageEntscheidung
UmschaltzeitpunktLive im Betrieb (kein Reboot, kein Flashen)
Auswahl-MechanismusRotary-Encoder-Geste (Empfehlung: Triple-Click)
BLE-RolleProxy bleibt in beiden Modi aktiv — gleiche Hardware, MIDI-In + BLE-Broadcast laufen unverändert weiter
Buildweiterhin als ANDRESGIT auf esp32-s3-devkitc-1; die Umschaltung ist rein intern

Kerngedanke: Beide Render-Profile werden in dasselbe Binary kompiliert; die wenigen verbliebenen Compile-Zeit-Entscheidungen werden auf bestehende Laufzeit-Variablen umgestellt (LEDGITBOARD und neu anz_LEDs).

4Konkrete Änderungen

4.1 — anz_LEDs: vom #define zur Laufzeit-Variable

In definitions.h ist anz_LEDs aktuell ein #define (Zeile 222 im NOMARKER-Block für ANDRESGIT-Test bzw. Zeile 312 im GITMARKER_GIT1-Block). Die Per-Device-Konstanten anz_LEDs_GIT1=163 / anz_LEDs_GITBOARD=278 (Zeile 182/184) bleiben #defines.

  • #define anz_LEDs … entfernen.
  • Globale Variable in main.cpp anlegen und in setup() initialisieren: 
    // main.cpp (global)
uint16_t anz_LEDs = anz_LEDs_GIT1;   // Startwert = Gitarren-Konfig
  • Deklaration in definitions.h (oder gemeinsamem Header): 
    extern uint16_t anz_LEDs;
  • Alle vorhandenen Nutzungen lesen anz_LEDs als Wert und funktionieren unverändert, u.a.: memset(leds,0,anz_LEDs*sizeof(CRGB)) (main.cpp:300, FXprograms.cpp:130), for (int i=0;i<anz_LEDs;i++) (FXprograms.cpp:517/568/591/1346/1672), random(0,anz_LEDs-50) (FXprograms.cpp:176).
Puffer bleiben NUMMATRIX-groß — nichts neu allokieren. anz_LEDs begrenzt lediglich, wie viele Pixel beschrieben/gelöscht werden.

4.2 — LEDGITBOARD zur umschaltbaren Variable machen

main.cpp:59-65: Die Variable existiert bereits, wird aber per #if defined(GITBOARD)||defined(SCROLLMATRIX) auf true initialisiert.

  • Für den ANDRESGIT-Build bleibt der Startwert false.
  • Die Deklaration extern uint16_t myRemapFn(uint16_t,uint16_t); (main.cpp:62) aus dem #ifdef-Block herausziehen, damit sie immer verfügbar ist.
// main.cpp – Ziel
boolean LEDGITBOARD = false;                          // umschaltbar zur Laufzeit
extern uint16_t myRemapFn(uint16_t x, uint16_t y);    // immer verfügbar

4.3 — Marker-Rendering per Laufzeit gaten statt NOMARKER

In markerLEDs.cpp:

  • setMarkerLEDs(): #if !defined(NOMARKER) (Zeile 21) → Laufzeit if (!LEDGITBOARD) { … }.
  • gitBlindingLEDs_OFF_MarkerLEDs_ON(): der Marker-Abschnitt #if !defined(NOMARKER) (Zeile 421) → if (!LEDGITBOARD) { … }.
  • extern boolean LEDGITBOARD; oben in markerLEDs.cpp ergänzen.
  • Die GITMARKER_GIT1-Indizes (Bund_min/max, ESaite_*, ASaite_*) bleiben einkompiliert.
Das memcpy(leds → leds1/leds2) (markerLEDs.cpp:417-418) kopiert immer den vollen Puffer (sizeof(leds)) und läuft in beiden Modi. Im GITBOARD-Modus wird weder der Fretboard-Bereich geschwärzt noch werden Marker gezeichnet; das 278-LED-Board hängt an einem Kanal und erhält das volle Bild über leds1 (DATA_PIN_1) → kein FastLED.addLeds-Umbau nötig.

4.4 — Matrix-Remap zur Laufzeit setzen / lösen

  • matrixFunctions.cpp:68: Der Guard #if defined(GITBOARD) um myRemapFn() (Definition Zeile 74) muss so erweitert werden, dass die Funktion immer kompiliert wird (Guard entfernen bzw. weiten).
  • main.cpp:170-172: Den bisher per #if defined(GITBOARD) gemachten setRemapFunction-Aufruf in die Toggle-Logik verlagern: 
    if (LEDGITBOARD) matrix->setRemapFunction(myRemapFn);
else             matrix->setRemapFunction(nullptr);   // ⚠ siehe Risiken
Zu verifizieren: ob setRemapFunction(nullptr) bei FastLED_NeoMatrix die eingebaute Zigzag-Anordnung (NEO_MATRIX_TOP+RIGHT+ROWS+ZIGZAG) wiederherstellt. Die Lib prüft i.d.R. if(remapFn) vor Nutzung — dann genügt nullptr. Falls nicht: eine Identitäts-/Standard-XY-Remap-Funktion für den Gitarren-Modus bereitstellen.

4.5 — Verbliebene #ifdef GITBOARD-Reste in FXprograms.cpp

Betroffen sind reine Text-/Scroll-Effekte, die ohnehin nur bei LEDGITBOARD==true laufen:

  • Cursor-Positionen FXprograms.cpp:1423-1427 und 1525-1529 (#if defined(GITBOARD) vs. SCROLLMATRIX): Da SCROLLMATRIX ein separater Build bleibt, im LEDGITBOARD-Pfad die GITBOARD-Werte verwenden und den #ifdef entfernen. 
    // vorher                          // nachher (innerhalb if (LEDGITBOARD) …)
#if defined(GITBOARD)              matrix->setCursor(progScrollTextZaehler, 13);
  matrix->setCursor(...,13);
#elif defined(SCROLLMATRIX)
  matrix->setCursor(...,1);
#endif
  • Scanner-/Zähler-Logik 1242 und 1280-1282 analog auf den LEDGITBOARD-Laufzeitpfad ziehen.
  • Die globalen outlinePath*[]-Arrays (108-124, SCROLLMATRIX vs. else=GITBOARD) bleiben unverändert: der Gitarren-Modus ruft progOutlinePath nicht auf, daher stören die GITBOARD-Indizes (>163) dort nicht.

4.6 — Umschalt-Geste im Rotary-Encoder

Bestehende Gesten in rotaryEncoder.cpp:

Gesteaktuelle Aktion
DrehenHelligkeit (rotary_loop, Z.184-197)
Short-ClickforceLEDsync (Proxy) bzw. needLEDsync (Client)
Double-ClickneedLEDsync vom Client anfordern (Proxy)

Empfehlung: Triple-Click als Umschalt-Geste — erweitert die vorhandene Single/Double-Erkennung (wasButtonDownFIRST/SECOND) um eine dritte Stufe und kollidiert weder mit Not-Aus noch mit Sync. Alternative: „Drücken + Drehen".

Der Triple-Click ruft die neue Funktion toggleLEDconfig() auf (siehe Abschnitt 5). Implementierung sinnvollerweise in main.cpp / functions.h (Zugriff auf matrix, switchToSong, Puffer), Aufruf aus dem Encoder per extern.

4.7 — Optional: Modus persistieren (NVS / Preferences)

Damit der zuletzt gewählte Modus einen Reboot übersteht: in toggleLEDconfig() per ESP32- Preferences speichern und in setup() lesen. Nicht zwingend für die Live-Umschaltung, aber komfortabel — als optionaler Folgeschritt umsetzbar.

5toggleLEDconfig() im Detail

Die zentrale neue Funktion. Sie wird durch die Encoder-Geste ausgelöst und stellt alle Laufzeit-Zustände konsistent um:

void toggleLEDconfig() {
    LEDGITBOARD = !LEDGITBOARD;

    // 1) LED-Anzahl umstellen
    anz_LEDs = LEDGITBOARD ? anz_LEDs_GITBOARD : anz_LEDs_GIT1;   // 278 / 163

    // 2) Matrix-Remap setzen/lösen
    if (LEDGITBOARD) matrix->setRemapFunction(myRemapFn);
    else             matrix->setRemapFunction(nullptr);   // ⚠ ggf. Identitäts-Remap

    // 3) Reste der anderen Konfiguration löschen
    FastLED.clear();
    memset(leds,  0, NUMMATRIX * sizeof(CRGB));
    memset(leds1, 0, NUMMATRIX * sizeof(CRGB));
    memset(leds2, 0, NUMMATRIX * sizeof(CRGB));

    // 4) Sauberer Neueinstieg
    switchToSong(0);
    #if defined(IS_MIDI_PROXY)
        forceLEDsync = true;     // Clients mitnehmen
    #endif

    // 5) optional: Preferences.putBool("ledcfg", LEDGITBOARD);

    Serial.println(LEDGITBOARD ? "MODE: GITBOARD (278)" : "MODE: ANDRESGIT (163)");
}
Da der Aufruf aus dem Encoder-Kontext kommt, sollte das eigentliche Umschalten möglichst außerhalb der LED-Render-Phase passieren (z.B. ein volatile bool requestConfigToggle setzen und im loop() vor dem flag_processFastLED-Block ausführen), um Race-Conditions mit einem laufenden FastLED.show() zu vermeiden.

7Wiederverwendete vorhandene Bausteine

  • LEDGITBOARD — bereits Laufzeit-Boolean, ~70 Nutzungen in songs.cpp.
  • switchToSong(0) / clearAll() (FXprograms.cpp:128) für sauberen Neustart.
  • myRemapFn() (matrixFunctions.cpp:74) für die GITBOARD-Matrix.
  • Bestehende Click-Erkennungs-Statemachine in rotaryEncoder.cpp (wasButtonDownFIRST/SECOND).
  • BLE-Proxy-Pfad (IS_MIDI_PROXY) bleibt unverändert aktiv — kein Eingriff nötig.

8Risiken & offene Punkte

  • Remap zurücksetzen: setRemapFunction(nullptr)-Verhalten der Lib verifizieren; ggf. Identitäts-Remap bereitstellen (siehe 4.4).
  • Timing/Race: Umschalten nicht mitten in einem FastLED.show() ausführen — Request-Flag im loop() abarbeiten (siehe 5).
  • Geister-LEDs: Beim Wechsel 163→278 vs. 278→163 sicherstellen, dass alle Puffer vollständig (über NUMMATRIX) gelöscht werden, damit keine Reste der anderen Konfig leuchten.
  • Helligkeit/Strom: 278 LEDs ziehen mehr Strom als 163 — DEFAULT_BRIGHTNESS ist konservativ (48); bei Bedarf je Modus anpassen.
  • Matrix-Orientierung: Beide Modi nutzen denselben „else"-Zweig (NEO_MATRIX_TOP+RIGHT+ROWS+ZIGZAG, main.cpp:151) — kein Unterschied, kein Eingriff nötig.
  • Lipo-Warn-LEDs nutzen feste Indizes 52/72 (main.cpp:434-440) — in beiden Modi gültig.

9Verifikation / Testplan

  1. Build: pio run -e esp32-s3-devkitc-1 (als ANDRESGIT) muss fehlerfrei kompilieren — insbesondere müssen myRemapFn und anz_LEDs linken (keine undefined reference).
  2. Gitarren-Modus (Default): Flashen, an die 163-LED-Gitarre anschließen. Songs/Marker verhalten sich exakt wie zuvor; Fret-Marker + Blinding-Off funktionieren.
  3. Umschalten: Triple-Click am Encoder → LEDs werden gelöscht, Modus wechselt (Serial @115200 loggt den Modus). An die 278-LED-Board-Konfiguration anschließen: Matrix-Remap aktiv, keine Marker, Text-/Scroll-Effekte und Outline-Pfade korrekt.
  4. Zurückschalten: Erneuter Triple-Click → zurück in den Gitarren-Modus; prüfen, dass der Remap sauber deaktiviert wird (keine verschobene/zerrissene Anzeige).
  5. BLE-Proxy: In beiden Modi prüfen, dass Song-/Part-Wechsel weiterhin an Clients (RINASBASS/LAMPEn) gebroadcastet werden (eine Lampe als Client mitlaufen lassen).
  6. Stabilität: Mehrfaches Hin-/Herschalten während ein Song läuft — auf Flackern/Hänger und korrekte LED-Anzahl (keine Geister-LEDs jenseits anz_LEDs) achten.
