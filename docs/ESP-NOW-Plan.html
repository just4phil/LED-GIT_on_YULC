LED-Sync per ESP-NOW

Plan: Alle Geräte stellen den LED-Sync von BLE auf ESP-NOW um, BLE wird abgeschaltet. Ziel ist ein genauerer gemeinsamer Start und Platz für beliebig viele Lampen. Das Abgleich-Protokoll (ledSync.cpp) bleibt unverändert. Stand 19.10.2026: Messung (Phase 0) erledigt, Entscheidung des Users nach der Messung: komplett umstellen, ohne dauerhafte Übergangszeit. #9–#13 umgesetzt im Branch espnow (19.10.2026), Probe mit allen Geräten (#16) steht aus.

1. Ziel & Kurzfassung

Heute hält jeder Client (Bass, Lampen, Matrix) eine eigene BLE-Verbindung zum Proxy. Die Grenze kommt aus der NimBLE-Konfiguration (CONFIG_BT_NIMBLE_MAX_CONNECTIONS=5 in platformio.ini) und aus der festen Adressliste client_addresses[] in midiProxyBLEserver_nimBLE.cpp. Außerdem wartet ein BLE-Notify auf das nächste Verbindungsereignis. Gemessen kommt eine Nachricht über BLE dadurch im Mittel 6,6 ms und bis zu 14,5 ms später an als über ESP-NOW (Phase 0, Abschnitt 8). Jedes Gerät hat dabei seinen eigenen Takt, so können die Geräte beim Songstart bis zu ~15 ms auseinander liegen.

Über Funk geht nur wenig: der Songstart (MIDI CC 22), ein von Hand gewählter Part (CC 23), der Abgleich per Drehknopf und der OTA-Befehl. Die automatischen Part-Wechsel rechnet jedes Gerät selbst über seinen Timer. Es reicht also, dieselbe kleine Nachricht gleichzeitig an alle zu schicken. Genau das kann ESP-NOW: ein Funkpaket von Espressif über das WLAN-Radio, ohne Router und ohne Verbindungsaufbau, als Broadcast an beliebig viele Empfänger.

Was gleich bleibt
  • Das Protokoll: BLEmessage (3 Bytes), die Nachrichtentypen 0–7, alle Entscheidungen in ledSync.cpp. Die 13 Tests in test/test_ledSync/ laufen unverändert.
  • Die Bedienung: Kurzklick = Abgleich, Doppelklick am Proxy = Stand holen, langer Druck = Not-Aus, Knopf beim Einschalten = OTA für alle. Die roten Warn-LEDs in Song 0, wenn der Funk fehlt.
Was sich ändert
  • Ein ESP-NOW-Adapter espNowSync.cpp ersetzt die beiden BLE-Adapter. Er schickt dieselbe BLEmessage in einem kleinen ESP-NOW-Rahmen.
  • Alle Geräte wechseln gleichzeitig: Gitarre, Bass, Lampe 1, Lampe 2, Matrix. Kein Gerät spricht beide Funkwege; es gibt keine dauerhafte Übergangszeit (Begründung in Abschnitt 3a).
  • Die Umstellung geschieht mit dem „OTA für alle“ der alten Firmware (Abschnitt 6a).
  • BLE bleibt eine Weile per Build-Flag als Rückweg im Code und wird nach den ersten erfolgreichen Auftritten entfernt.
  • Danach können neue Lampen dazukommen, zuerst als Klone von Lampe 1/2, später mit eigener Identität.

3. Zielbild

Schichten

Die Trennung „Logik entscheidet, Adapter führt aus“ aus dem LED-Sync-Umbau bleibt. Heute steckt applyAction() in den beiden BLE-Dateien. Damit der Funkweg austauschbar wird, wandert applyAction() in zwei transportneutrale Dateien (syncProxy, syncClient). Welcher Funkweg gebaut wird, entscheidet ein Build-Flag für alle Geräte gemeinsam: ESP-NOW (Standard) oder BLE (Rückweg, bis BLE entfernt wird).

3a. Was bringt es? (gemessen in Phase 0)

Besser

  • Genauerer gemeinsamer Start (der Hauptgewinn, vom User gewünscht): BLE kam im Mittel 6,6 ms, höchstens 14,5 ms später als ESP-NOW. Ein ESP-NOW-Broadcast erreicht alle praktisch gleichzeitig; die Funkzeit liegt geschätzt bei ~2 ms. Bei 120 BPM sind 15 ms etwa 3 % eines Beats, sichtbar am ehesten bei Blindern und harten Schnitten.
  • Nach einem Funkabriss hört ein ESP-NOW-Gerät sofort wieder mit. Ein BLE-Client sucht heute in 10-s-Runden und muss sich dann neu verbinden.
  • Kurzklick am Client: readValue() blockiert heute loop(), bis der Proxy antwortet. Mit ESP-NOW wird das eine Anfrage, auf die loop() nicht wartet.
  • Beliebig viele Geräte, keine Adressliste mehr.
  • Weniger Flash: NimBLE fällt weg; WLAN ist wegen OTA schon in der Firmware.

Gleich

  • Gleichlauf im Song: keine Änderung. Die Part-Wechsel rechnet jedes Gerät nach seinem eigenen Timer, über Funk kommt nur der Start.
  • Bildrate: praktisch gleich, FastLED.show() kostet die meiste Zeit.
  • Strom: gemessen an der Gitarre: Das reine ESP-NOW-Radio kostet 35 mA, BLE + Marker-LEDs heute ~42 mA. Kein spürbarer Unterschied.
  • Flackern: keins, weder im Messprogramm noch mit echter Firmware und Show.

Warum keine dauerhafte Übergangszeit

Ursprünglich sollte der Proxy eine Weile beide Funkwege bedienen: BLE für die alten Geräte, ESP-NOW für neue Lampen. Die Messung spricht dagegen:

  • Laufen BLE und WLAN gleichzeitig, teilen sie sich das Radio. ESP-NOW kam dann in 4 von 38 Fällen bis 4,8 ms nach BLE an. Erst ohne BLE ist ESP-NOW wirklich pünktlich.
  • Mit beiden Funkwegen verlangt das ESP-IDF WLAN-„Modem Sleep“; ohne Bluetooth darf Stromsparen ganz aus.
  • Beide Wege parallel bedeuten mehr Code: Der Proxy müsste doppelt senden, und jeder Client bräuchte die Wahl des Funkwegs.
  • Eine Übergangs-Firmware ist für die Umstellung nicht nötig (Abschnitt 6a).

4. Der ESP-NOW-Rahmen (Wire-Format)

Ein ESP-NOW-Paket darf bis zu 250 Bytes tragen. Wir brauchen 13. Die BLEmessage steckt unverändert darin, davor ein kleiner Kopf:

// espNowFrame.h (Entwurf)
#pragma pack(push, 1)
struct EspNowFrame {
    uint8_t    magic[2];   // 'L','S' - "LED-Sync": Pakete anderer ESP-NOW-Geräte fallen sofort heraus
    uint8_t    version;    // 1 - steigt nur, wenn sich dieser Rahmen ändert
    uint8_t    kind;       // EspNowKind (Tabelle unten)
    uint16_t   bootId;     // Zufallszahl je Start des Absenders
    uint16_t   seq;        // Sequenznummer, +1 je neuer Nachricht (Wiederholungen behalten sie)
    uint8_t    copy;       // 0, 1, 2 = Original bzw. 1./2. Wiederholung
    uint8_t    device;     // Absender-Gerät (DEV_ME-Bit bzw. Geräte-Nummer), für Anzeige/OTA-Zählung
    BLEmessage msg;        // die 3 Bytes aus ledSync.h, unverändert
};
#pragma pack(pop)
static_assert(sizeof(EspNowFrame) == 13, "EspNowFrame muss genau 13 Bytes gross sein");
kindRichtungBedeutungBLE-Gegenstück
KIND_MSG = 1Proxy → alle (Broadcast)eine Nachricht mit notify = trueNotify
KIND_READ_REQ = 2Client → Proxy (gezielt)„schick mir deinen hinterlegten Stand“Read (Anfrage)
KIND_READ_RESP = 3Proxy → Client (gezielt)der zuletzt hinterlegte Wert (SYNC_STATE oder SYNC_ENTRY)Read (Antwort)
KIND_WRITE = 4Client → Proxy (gezielt)SYNC_REPLY / SYNC_ENTRY nach einem DoppelklickWrite
KIND_HELLO = 5Proxy → alle (Broadcast), ca. 1 s„ich bin da“, Inhalt = hinterlegter StandAdvertising / Verbindung
KIND_HELLO_ACK = 6Client → Proxy (gezielt)„ich höre dich“ - für Warn-LEDs und OTA-Zählung am ProxySubscribe
Warum die Art im Rahmen steht und kein neuer msgType: Die Nachrichtentypen 0–7 sind festgeschrieben. Lesen, Schreiben und „ich bin da“ sind bei BLE Teil der Verbindung, nicht der Nachricht. Bei ESP-NOW übernimmt das Feld kind diese Rolle. Die BLEmessage bleibt so byte-gleich (wichtig für den BLE-Rückweg), und ledSync.cpp sieht von alldem nichts.

Gezielte Pakete gehen an die MAC-Adresse der Gegenseite. Der Client lernt die Proxy-Adresse aus dem ersten gültigen HELLO oder MSG (Absenderadresse im Empfangs-Callback) und trägt sie als ESP-NOW-Peer ein. Der Proxy trägt einen Client nur kurz als Peer ein, um ihm zu antworten (ESP-NOW erlaubt höchstens 20 Peers, Broadcast braucht nur einen: FF:FF:FF:FF:FF:FF).

Reiner Teil, am PC testbar

Nach dem Vorbild von ledSync.cpp kommt alles, was ohne Funk geht, in espNowFrame.cpp (kein Arduino):

  • espNowEncode(kind, bootId, seq, copy, device, msg, buf) und espNowDecode(buf, len, frame) (prüft Länge, Magic, Version)
  • Duplikat-Filter espNowIsNew(senderMac, bootId, seq): neu, wenn die Boot-ID wechselt oder (int16_t)(seq - lastSeq) > 0 (übersteht den Überlauf bei 65535)
  • Peer-Tabelle mit „zuletzt gehört“: espNowSeen(mac, device, nowMs), espNowCountAlive(nowMs, maxAgeMs)

5. Zuverlässigkeit & Timing

Verlorene Pakete

Ein Broadcast wird vom Empfänger nicht bestätigt. Deshalb geht jede Proxy-Nachricht 3-mal hinaus, im Abstand von ESPNOW_REPEAT_MS (3 ms), mit derselben Sequenznummer und copy = 0, 1, 2. Der Empfänger nimmt die erste Kopie, die ankommt, und verwirft die anderen. Gesendet werden die Wiederholungen ohne delay(): Der Adapter merkt sich die offenen Kopien und schickt sie in espNowSync_Loop(), sobald ihre Zeit da ist. Gemessen (durch eine Wand): ohne Wiederholung ~5 % Verlust je Richtung, mit 3 Wiederholungen nur noch 0,1–0,6 % für Hin und Rück zusammen.

Gezielte Pakete (Lesen, Schreiben, HELLO_ACK) bestätigt ESP-NOW selbst auf Funkebene und wiederholt sie bei Bedarf. Der Sende-Callback meldet Erfolg oder Fehler; bei Fehler einmal neu senden.

Zeitgenauigkeit

  • Ein ESP-NOW-Paket ist in ~2 ms beim Empfänger (gemessen ~3 ms inkl. Loop-Wartezeit). Bei BLE wartet ein Notify auf das nächste Verbindungsereignis, gemessen bis 14,5 ms.
  • Kommt nur eine Wiederholung an, ist sie 3 oder 6 ms zu spät. Laut Messung ist das selten; ein Ausgleich über das Feld copy ist deshalb nicht vorgesehen (#15 geschlossen). Das Feld bleibt im Rahmen, falls es später gebraucht wird.
  • Der Empfangs-Callback läuft im WLAN-Task, nicht in loop(). Er legt das Paket nur in einen kleinen Ringpuffer (8 Plätze, geschützt mit portMUX/portENTER_CRITICAL). Ein einzelner „Briefkasten“ wie heute in BLE_client_nimBLE.cpp reicht nicht, weil z.B. HELLO und eine Nachricht kurz hintereinander kommen können.

Funkeinstellungen

  • WiFi.mode(WIFI_STA), WiFi.disconnect(), fester Kanal esp_wifi_set_channel(ESPNOW_CHANNEL, WIFI_SECOND_CHAN_NONE). Alle Geräte müssen denselben Kanal haben.
  • Stromsparen aus: esp_wifi_set_ps(WIFI_PS_NONE), sonst verschläft der Empfänger Pakete. Das geht nur ohne Bluetooth: Läuft BLE gleichzeitig (BLE-Rückweg ist ein eigener Build, also nie), verlangt das ESP-IDF WIFI_PS_MIN_MODEM, sonst startet das Gerät endlos neu (gemessen 19.10.2026).
  • Volle Sendeleistung (WiFi.setTxPower(WIFI_POWER_19_5dBm)), wie heute bei BLE ESP_PWR_LVL_P9.
  • Optional: Espressif-Langstreckenmodus (WIFI_PROTOCOL_LR), falls die Reichweite knapp ist. Muss dann auf allen Geräten gleich sein.
  • Grundlage: Arduino-Core 2.0.17 (ESP-IDF 4.4, Plattform espressif32 6.10.0). Dort hat der Empfangs-Callback die Form void cb(const uint8_t* mac, const uint8_t* data, int len). Erprobt im Messprogramm tools/espnow-spike/ (Branch espnow-spike).
  • Das Bluetooth der YULC-Boards wird in der ESP-NOW-Firmware gar nicht gestartet.

Fremde Sender (Sicherheit)

Broadcasts lassen sich bei ESP-NOW nicht verschlüsseln, jedes ESP-Gerät auf dem Kanal hört mit und kann senden. Vorgabe des Users (19.10.2026): Clients nehmen nur Pakete von der Gitarre an, andere Absender gibt es nicht. Umgesetzt: Die WLAN-MAC der Gitarre steht fest als ESPNOW_PROXY_MAC in definitions.h; jedes Paket einer anderen Adresse wird verworfen. Die Adresse setzt die Funk-Hardware des Absenders, sie steht nicht im Paketinhalt. Zusätzlich: Magic, Version, Länge, Geräte-Bit und Paketart müssen passen. Gegen jemanden, der gezielt die MAC der Gitarre fälscht, schützt das nicht (dafür bräuchte es eine Signatur je Paket, z.B. HMAC mit gemeinsamem Schlüssel); gegen jedes andere ESP-NOW-Gerät in der Halle schon.

Die MAC der Gitarre (48:CA:43:80:8B:94) ist aus ihrer Bluetooth-Adresse abgeleitet (− 1, wie bei Lampe 1 gemessen) und am 19.10.2026 bestätigt: alle Clients folgen der Gitarre. Bei einem Board-Tausch gilt: Beim ersten Start der ESP-NOW-Firmware gibt die Gitarre ihre echte MAC auf Serial aus (ESP-NOW: aktiv auf Kanal 1, MAC …) - stimmt sie nicht, hören die Clients nichts (rote Warn-LEDs). Dann den Wert in definitions.h korrigieren.

6. Abläufe Schritt für Schritt

Jeder Ablauf endet in denselben ledSync-Funktionen wie heute. Neu ist nur, wie die Bytes reisen.

MIDI-Wechsel (Songstart, Part-Sprung)

  1. CC 22/23 → ledSyncProxyMidiSong/Part().
  2. ledSyncProxyLoop() → Zettel mit SYNC_SONG bzw. SYNC_PART, notify.
  3. syncProxy: KIND_MSG als Broadcast, 3 Kopien.
  4. Clients: erste Kopie → ledSyncClientReceived() → switchToSong(); weitere Kopien verworfen.

Abgleich erzwingen (Kurzklick am Proxy, Not-Aus): 3 → 4

  1. Proxy sendet SYNC_FORCE an alle (Broadcast). Clients springen, schalten dunkel, warten.
  2. Beim nächsten Part-Wechsel des Proxys: SYNC_ENTRY an alle. Wartende Clients starten den Part zeitgleich.

Stand lesen (Kurzklick am Client): READ_REQ → READ_RESP → 4

  1. ledSyncClientLoop() liefert readProxy = true.
  2. Client sendet KIND_READ_REQ gezielt an den Proxy. Anders als BLE-readValue() wartet er nicht: Die Antwort kommt später in espNowSync_Loop() an.
  3. Proxy: Empfang → ledSyncProxyClientRead() (wie onRead()) und Antwort KIND_READ_RESP mit seinem zuletzt hinterlegten Wert. Den Wert führt der Adapter selbst mit: Jeder Eintrag auf dem Zettel - ob notify oder nicht - überschreibt ihn, genau wie heute storeMessage(). Damit bleibt auch „Eigenheit 2“ (nach SYNC_ENTRY liest man Song 0) gleich.
  4. Client: ledSyncClientReadResult() → springen, auf SYNC_ENTRY warten.
  5. Kommt innerhalb von ~200 ms keine Antwort, Anfrage einmal wiederholen; danach aufgeben (wie heute: Knopf noch einmal drücken).

Stand abfragen (Doppelklick am Proxy): 5 → 6 → 4

  1. Proxy sendet SYNC_ASK an alle.
  2. Jeder Client antwortet mit SYNC_REPLY (KIND_WRITE gezielt an den Proxy) und meldet seinen nächsten Part-Wechsel mit SYNC_ENTRY.
  3. Proxy: ledSyncProxyClientWrote() → springen.
Wie heute antworten alle Clients; der Proxy springt bei jeder Antwort, die letzte gewinnt. Mit vielen Lampen gibt es mehr Antworten, sie stehen aber normalerweise alle auf demselben Stand. Das Verhalten bleibt bewusst wie es ist (LED-Sync-Entscheidung vom 18.10.2026). Damit die Antworten nicht genau gleichzeitig senden, wartet jeder Client vor dem Senden eine kleine, geräteabhängige Zeit (z.B. 2 ms × Geräte-Nummer) - reine Transportsache.

Verbindungsanzeige (rote Warn-LEDs in Song 0)

  • Client: „verbunden“ = in den letzten ESPNOW_LINK_TIMEOUT_MS (Vorschlag 3000) ein gültiges Paket vom Proxy gehört (espNowSync_isLinked()).
  • Proxy: „mindestens ein Client da“ = mindestens ein Client mit frischem HELLO_ACK (espNowSync_seenClients()).
  • Die Warnlogik in markerLEDs.cpp fragt künftig syncLinkMissing(), die je nach gebautem Funkweg die richtige Quelle nimmt.

OTA für alle (Knopf beim Einschalten)

  1. Proxy startet ESP-NOW, sendet HELLO im Takt und wartet (wie heute höchstens OTA_CLIENT_WAIT_MS), bis ESPNOW_EXPECTED_CLIENTS Clients mit HELLO_ACK da sind. Bis die Zählung fertig ist (#13), wartet er einfach eine feste Zeit.
  2. SYNC_SONG 0, dann 3× SYNC_OTA per Broadcast. Hier ist delay() weiter erlaubt (läuft in setup()).
  3. Nach dem Neustart läuft otaRun() in einem eigenen Boot und verbindet sich mit dem Router-WLAN. ESP-NOW ist in diesem Boot nicht gestartet, es gibt keinen Konflikt mit dem Kanal.

6a. Die Umstellung aller Geräte

Eine Übergangs-Firmware, die beide Funkwege spricht, ist nicht nötig. Den Update-Befehl gibt nämlich noch die alte Firmware:

  1. Vorbereiten: python tools/build_ota.py baut die ESP-NOW-Firmware für alle Geräte (Claude baut; den Server startet der User mit --serve-only). Alle Geräte im Proberaum, Akkus voll.
  2. OTA für alle mit der alten Firmware: Gitarre mit gedrücktem Knopf einschalten. Sie schickt den Befehl wie gewohnt per BLE an alle, alle Geräte laden die neue Firmware.
  3. Ab jetzt sprechen alle ESP-NOW. Kontrolle: Warn-LEDs aus, Songstart per MIDI, Kurzklick.
  4. Hat ein Gerät das Update verpasst, hört es nichts mehr (es spricht noch BLE). Es wird per USB geflasht (pio run -e <gerät> -t upload).
  5. Weitere Updates laufen über das „OTA für alle“ der neuen Firmware per ESP-NOW.
Rückweg: Solange der BLE-Code noch im Repo ist, lässt sich mit dem Build-Flag eine BLE-Firmware bauen. Weil OTA nur eine neuere Version lädt, bekommt sie automatisch eine neue Versionsnummer (tools/fw_version.py) und lässt sich per „OTA für alle“ (jetzt per ESP-NOW ausgelöst) wieder auf alle Geräte bringen. Zur Not per USB.

Gerät verpasst die UmstellungEs spricht noch BLE und hört nichts mehr Umstellung im Proberaum, Gerät per USB nachflashen (Abschnitt 6a).
PaketverlustEin Gerät verpasst Songstart oder SYNC_ENTRY 3 Wiederholungen + Dedup (gemessen: ausreichend); im Ernstfall wie heute Kurzklick = Abgleich.

Störendes Hallen-WLANViele Netze auf dem gewählten Kanal Kanal 1, 6 oder 11 fest wählen, bei Bedarf per Build umstellen (alle Geräte gleich, OTA für alle).
