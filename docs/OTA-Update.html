OTA-Firmware-Update über WLAN

Alle Geräte auf einmal aktualisieren, ohne USB-Kabel: bauen am PC, Gitarre mit gedrücktem Knopf einschalten, fertig. Stand 28.09.2026, Branch ota.

1 · Überblick

Das Update ist ein Pull-Modell: Der PC stellt die fertigen Firmwares per HTTP bereit. Jedes Gerät holt sich seine eigene Datei selbst, aber nur wenn sie neuer ist als die installierte. Ausgelöst wird das Ganze von der Gitarre (MIDI-Proxy), die per BLE ohnehin mit allen anderen Geräten verbunden ist.

Wichtig für das Verständnis: WLAN und BLE laufen nie gleichzeitig. Ein Gerät, das updaten soll, merkt sich das in einem Flag im Flash (NVS) und startet neu. Im nächsten Start sieht setup() das Flag und geht direkt in den Update-Modus. BLE, Timer und Effekte werden dann gar nicht erst gestartet. Nach dem Update (oder einem Fehler) startet das Gerät wieder ganz normal.

2 · Kurzanleitung

  1. Alle Geräte (außer Gitarre) einschalten und normal laufen lassen.
  2. Am PC: python tools/build_ota.py --serve (baut alles, startet Server, Fenster offen lassen).
  3. Gitarre mit gedrücktem Rotary-Knopf einschalten, Knopf ca. 1–2 s halten, bis die LEDs lila werden.
  4. Warten: lila (Gitarre sammelt Clients) → blau (WLAN) → gelb (Download) → grün. Danach laufen alle Geräte mit der neuen Firmware.
  5. Kontrolle: im Server-Fenster steht je Gerät ein GET /<gerät>/firmware.bin … 200.

3 · Einmalige Einrichtung

  1. WLAN-Zugang anlegen du
    Vorlage kopieren und ausfüllen. Die Datei ist gitignored und landet nie im Repo. 
    copy src\secrets.h.example src\secrets.h
    // src/secrets.h
#define OTA_WIFI_LIST { \
	{ "Heim-WLAN",		"passwort" }, \
	{ "Laptop-Hotspot",	"passwort" }, \
}
#define OTA_SERVER	"192.168.137.1"	// IP des PCs mit build_ota.py --serve
#define OTA_PORT	8080
    Mehrere WLANs sind erlaubt, das Gerät nimmt das stärkste gefundene. OTA_SERVER ist eine feste IP, sie muss in jedem eingetragenen WLAN stimmen. Am einfachsten ist deshalb der Windows-Mobile-Hotspot des Laptops: Dort hat der Laptop immer 192.168.137.1, egal wo du bist. 2,4 GHz einstellen (der ESP32-S3 kann kein 5 GHz).
  2. Jedes Gerät einmal per USB flashen du
    Die OTA-Funktion muss einmal auf dem Gerät sein, bevor es sich per WLAN updaten kann. Ab dann geht alles drahtlos. 
    pio run -e andresgit    -t upload --upload-port COM8
pio run -e rinasbass    -t upload --upload-port COM9
pio run -e lampe1       -t upload --upload-port COM11
pio run -e lampe2       -t upload --upload-port COM10
pio run -e scrollmatrix -t upload --upload-port COMx   // Port prüfen, s. Kap. 8
    Im seriellen Monitor erscheint beim Start z. B. FIRMWARE lampe1 - Version 1790604888 (a5ea119).
  3. Windows-Firewall freigeben du
    Beim ersten --serve fragt Windows, ob Python im Netzwerk erreichbar sein darf. Zulassen, und zwar auch für „Öffentliche Netzwerke“, denn der Hotspot gilt oft als öffentlich. Ohne Freigabe sehen die Geräte den Server nicht (Fehler „HTTP -1“).

4 · Update Schritt für Schritt

  1. Code ändern und committen du
    Nicht zwingend, aber dann steht im Log ein sauberer Git-Hash. Mit ungespeicherten Änderungen hängt ein + am Hash (z. B. a5ea119+).
  2. Bauen und Server starten build_ota.py 
    python tools/build_ota.py --serve            # alle 5 Geräte
python tools/build_ota.py lampe1 lampe2 --serve   # nur einzelne
python tools/build_ota.py --serve-only       # nichts bauen, nur ausliefern
    Vor dem Bauen fragt das Skript, ob der bisherige Stand aus ota/ gesichert werden soll (s. unten, „Backups“). Mit j antworten, wenn der aktuelle Stand gut funktioniert hat. Das Skript zeigt die Größe jeder Firmware und die IP-Adressen des PCs. Eine davon muss OTA_SERVER sein. Das Fenster offen lassen, solange das Update läuft.
  3. Geräte einschalten du
    Bass, Lampen, Scrollmatrix laufen normal im Leerlauf (Song 0). Die Gitarre ist noch aus.
  4. Gitarre mit gedrücktem Knopf einschalten du
    Rotary-Knopf drücken, einschalten, mindestens 1 s halten. Die LEDs der Gitarre werden lila: Sie wartet, bis alle vier Clients verbunden sind. Der lila Balken wächst mit jedem verbundenen Client (max. 20 s). Ist ein Gerät aus, geht es weiter, sobald sich 5 s lang kein weiterer Client mehr angemeldet hat.
  5. Automatisch: Befehl an alle Gitarre
    Die Gitarre schaltet alle Clients auf Song 0, schickt 3× den Update-Befehl und startet dann selbst im Update-Modus neu.
  6. Automatisch: jedes Gerät lädt alle Geräte
    Blau blinkend = WLAN-Suche, gelber Balken = Download, grün = fertig. Danach Neustart mit der neuen Firmware. Ein Gerät, das schon aktuell ist, zeigt nur kurz grün und startet normal.
  7. Kontrollieren du
    Im Server-Fenster muss je Gerät GET /<gerät>/version.json und (wenn neuer) GET /<gerät>/firmware.bin mit 200 stehen. Ein Gerät, das rot geblinkt hat, läuft mit der alten Firmware weiter: Kap. 13.
Nur ein einzelnes Gerät updaten geht genauso: Der Ablauf schickt immer alle in den Update-Modus, aber nur Geräte mit neuerer Version auf dem Server laden etwas herunter. Die anderen zeigen kurz grün und starten normal.

6 · Was intern passiert

Gitarre (Proxy) beim Einschalten mit Knopf

  1. setup() initialisiert die LEDs, dann otaIsRequested() (normalerweise false).
  2. otaBootButtonHeld() prüft ROTARY_ENCODER_BUTTON_PIN (GPIO 4, Pull-up, gedrückt = LOW): Bleibt der Knopf 1 s gedrückt → true. Ist er gar nicht gedrückt, kostet das nur ca. 5 ms Startzeit.
  3. midiProxy_initialize_BLE() startet den BLE-Server wie immer, direkt danach midiProxy_broadcastOTA():
    • wartet, bis subscribedClients ≥ Anzahl erlaubter Clients (4), max. 20 s (OTA_CLIENT_WAIT_MS). Gezählt wird im onSubscribe-Callback: Erst wer Notifications abonniert hat, empfängt den Befehl sicher.
    • bricht das Warten früher ab, wenn mindestens ein Client da ist und sich 5 s lang (OTA_CLIENT_QUIET_MS) kein weiterer angemeldet hat: Die fehlenden Geräte sind dann wohl aus. Solange noch gar kein Client da ist, läuft die volle Zeit.
    • sendet msgType 1 / Song 0 (alle auf SONGPAUSE), 500 ms Pause.
    • sendet 3× msgType 7 im Abstand von 500 ms (falls eine Notification verloren geht).
    • 1 s warten, dann otaRequestAndRestart().

Client beim Empfang von msgType 7

MidiDatenVomProxyAuswerten() in BLE_client_nimBLE.cpp, case 7: Nur wenn songID == 0 → otaRequestAndRestart(). Während eines Songs wird der Befehl ignoriert. Das ist der Schutz gegen ein Update mitten im Gig.

Update-Modus (alle Geräte)

  1. otaRequestAndRestart(): NVS-Namespace ota, Key req = true, dann ESP.restart().
  2. Neustart → setup() → otaIsRequested() liest das Flag und löscht es sofort. Dadurch kann es keine Boot-Schleife geben: Auch wenn das Update abbricht, ist der nächste Start normal.
  3. otaRun() (kehrt nie zurück):
    • WLAN per WiFiMulti mit allen SSIDs aus OTA_WIFI_LIST: Suchen + Anmelden, je Versuch max. 8 s, insgesamt max. 20 s.
    • GET http://OTA_SERVER:OTA_PORT/<DEVICE_NAME>/version.json
    • Server-version ≤ eigene FW_VERSION → grün, Neustart ohne Download.
    • sonst GET …/firmware.bin → Update.begin(size), Update.setMD5(md5), Update.writeStream(), Update.end(). Die Firmware wird in den gerade nicht laufenden App-Slot geschrieben. Update.end() prüft MD5 und Image und schaltet erst dann den Boot-Slot um.
    • grün, 2 s, Neustart → neue Firmware startet normal.
  4. Jeder Fehler (kein WLAN, HTTP ≠ 200, falsche Größe, MD5 falsch) → otaFail(): rot blinken, Neustart. Der Boot-Slot wurde nicht umgeschaltet → alte Firmware.

7 · Versionen & Backups

  • FW_VERSION = Unix-Zeit (Sekunden) des Builds, z. B. 1790604888. Steigt immer, ein einfacher Zahlenvergleich reicht.
  • FW_GIT = kurzer Git-Hash von HEAD, mit + wenn es ungespeicherte Änderungen gab. Nur zur Info, wird nicht verglichen.
  • Gesetzt von tools/fw_version.py (PlatformIO extra_scripts = pre:). Die Defines gelten nur für src/otaUpdate.cpp (Build-Middleware). Eine neue Version kompiliert also nur diese eine Datei neu, nicht das ganze Projekt. Andere Dateien lesen die Version über otaFirmwareVersion() / otaFirmwareGit().
  • build_ota.py setzt die Umgebungsvariable FW_VERSION einmal für alle Geräte eines Laufs → alle bekommen dieselbe Nummer. Normale Builds (z. B. USB-Upload aus VS Code) nehmen die aktuelle Uhrzeit.
Folge: Ein Gerät lädt nur, was später gebaut wurde als seine eigene Firmware. Hast du nach dem letzten build_ota.py ein Gerät per USB geflasht, ist dessen Version neuer → es ignoriert den Server. Einfach build_ota.py neu laufen lassen. Zurück auf eine ältere Firmware geht per Backup (--restore, s. unten), per Neubau des alten Stands oder per USB.

Backups & Zurückspielen

  • Vor jedem Bauen fragt build_ota.py: „Bisherigen Stand (…; gebaut 28.09.2026 23:01) als Backup sichern? [j/N]“. Bei j werden alle Geräte-Ordner aus ota/ nach ota/backup/JJJJ-MM-TT/ kopiert (firmware.bin + version.json). Ein zweites Backup am selben Tag landet in …_2, …_3 usw. Enter = kein Backup.
  • Ohne Frage: --backup (immer sichern) oder --no-backup (nie). Läuft das Skript ohne Konsole (keine Eingabe möglich), wird ohne --backup nichts gesichert.
  • Gefragt wird nur, wenn in ota/ schon etwas liegt. Gesichert wird immer der ganze bisherige Stand, auch wenn nur einzelne Geräte neu gebaut werden.
  • Zurückspielen: python tools/build_ota.py --restore 2026-09-28 --serve kopiert die Geräte aus dem Backup zurück nach ota/ und gibt ihnen eine neue Versionsnummer (jetzt). Sonst würden die Geräte die ältere Firmware nicht laden. In version.json steht dann "restored_from" mit Backup-Name und ursprünglicher Version. Vorher kommt dieselbe Backup-Frage für den aktuellen Stand.
  • Die Backups liegen im gitignored ota/-Ordner, also nur auf diesem PC, und werden vom Server mit ausgeliefert (harmlos, die Geräte fragen nur ihren eigenen Ordner ab). Aufräumen von Hand.

version.json

{
 "version": 1790604888,
 "git": "a5ea119",
 "md5": "652f0c9c5b3345a56a53aaa58518d25a",
 "size": 1155488
}

Das Gerät liest die Felder mit einem Mini-Parser (jsonValue() in otaUpdate.cpp), keine JSON-Bibliothek. Das Format muss flach bleiben (keine verschachtelten Objekte). size wird nicht ausgewertet, die Größe kommt aus dem HTTP-Header.

9 · BLE-Protokoll

Struktur BLEmessage (functions.h), 3 Bytes, gepackt: msgType, songID, part. Eine Characteristic mit READ/WRITE/NOTIFY.

msgTypeRichtungBedeutung
0ProxySong + Part setzen (Wert zum Lesen für Sync)
1Proxy → ClientsSong wechseln (songID)
2Proxy → ClientsPart wechseln (part)
3Proxy → ClientsSync erzwingen (Song + Part)
4beidePart wechseln nach LED-Sync
5Proxy → ClientsProxy braucht LED-Sync von einem Client
6Client → ProxyClient meldet Song/Part nach Sync-Anfrage
7Proxy → ClientsIn den OTA-Update-Modus (nur angenommen bei songID == 0)

Welche Clients der Proxy überhaupt akzeptiert, steht in client_addresses[] in midiProxyBLEserver_nimBLE.cpp. Deren Anzahl ist auch die Zahl, auf die midiProxy_broadcastOTA() wartet.

14 · Grenzen & Risiken

  • Kein automatischer Rollback. Startet die neue Firmware, aber stürzt später ab, bleibt sie aktiv. Der Arduino-Core hat die Rollback-Funktion des Bootloaders standardmäßig aus. Notfallweg ist immer USB. Deshalb: neue Firmware erst an einem Gerät per USB testen, dann per OTA an alle.
  • WLAN-Daten sind einkompiliert. Neues WLAN = secrets.h ändern, bauen, per OTA verteilen (solange das alte WLAN noch geht), sonst per USB.
  • Keine Verschlüsselung / Signatur. HTTP ohne TLS. Wer im selben WLAN einen Server unter OTA_SERVER betreibt, könnte Firmware einspielen, aber nur während ein Update ausgelöst ist. Für ein privates Heim-/Hotspot-Netz vertretbar.
  • Auslöser nur über die Gitarre. Die Lampen haben keinen Knopf. Ohne laufende Gitarre (Proxy) gibt es kein OTA für die Clients.
  • Nie auf der Bühne. Clients nehmen den Befehl nur im Leerlauf an, und die Gitarre startet OTA nur mit gedrücktem Knopf beim Einschalten. Im Gig-Betrieb passiert also nichts, außer jemand hält beim Einschalten den Knopf.

15 · Erweitern

Neues Gerät hinzufügen

  1. definitions.h: Geräte-Block mit Features, im DEV_ME-Block ein DEVICE_NAME ergänzen, das Define in die Fallback-Bedingung (#if !defined(ANDRESGIT) && …) aufnehmen.
  2. platformio.ini: neues Env mit extends = esp32_base und build_flags = ${esp32_base.build_flags} -D NEUESGERAET.
  3. tools/build_ota.py: Env-Name in DEVICES aufnehmen.
  4. Ist es ein BLE-Client: MAC in definitions.h und in client_addresses[] (midiProxyBLEserver_nimBLE.cpp) eintragen. Sonst akzeptiert der Proxy es nicht und wartet beim OTA vergeblich darauf.
  5. Einmal per USB flashen.

Ideen für später

  • Server-Adresse automatisch finden (z. B. Gateway-IP oder mDNS) statt fester OTA_SERVER.
  • Rollback aktivieren (eigener Bootloader mit CONFIG_APP_ROLLBACK_ENABLE, Firmware bestätigt sich nach erfolgreichem Start).
  • Zusätzlicher Auslöser per MIDI-CC vom WIDI.
Pflege: Diese Seite ist die Referenz für alles rund um OTA. Bei jeder Änderung an otaUpdate.*, am BLE-Protokoll, an den Geräte-Envs, an build_ota.py/fw_version.py oder an den Partitionen wird sie mit angepasst.
