## Project Overview

**Platform:** ESP32 / Teensy (via PlatformIO)

## 1. Architectural Analysis

### Current State
The project follows a **procedural architecture** heavily dependent on **global state** and **large switch-case statements**.
- **`main.cpp`**: Controls the core loop and handles high-level song selection.
- **`songs.cpp`**: Contains the state machines for every song.
- **`definitions.h`**: Manages hardware configurations via `#define` macros.

### Identified Challenges
1. **Scalability**: Adding a new song involves adding a new case in the main loop and creating a new function in `songs.cpp` with its own nested switch-case. This leads to a "Mega-File" antipattern (e.g., `songs.cpp` is >3,300 lines).
2. **Global State Complexity**: Variables like `songID`, `prog`, `flag_processFastLED`, etc., are declared `extern` and accessed/modified from multiple files, making debugging and state tracking difficult.
3. **Tight Coupling**: Song logic is tightly coupled with timing logic (`millisCounterTimer`) and specific FX calls.

---

## 2. Performance & Stability

### Current State
- **Main Loop**: Uses a 2ms "time-slot" pattern (`flag_processFastLED`) to maintain timing accuracy.
- **Safety**: Includes `HAS_LIPOVOLTAGE_CHECK` to protect batteries.
- **Interrupts**: Uses timers/ISRs for background processing.

### Identified Improvements
1. **Timing Jitter**: Manually checking `flag_processFastLED` in `loop()` can introduce jitter if other tasks (like BLE/MIDI) block the loop.
2. **Memory Usage**: The use of multiple large LED arrays (`leds`, `leds1`, `leds2`) consumes significant RAM.
3. **Redundant Logic**: Many song parts essentially repeat the same patterns with different timing parameters.

---

## 3. Recommended Optimizations

### High Priority: Data-Driven Song Engine
Replace the complex switch-case structures with a **Data-Driven Model**.
- **Proposal**: Define a `SongPart` struct and a `Song` class.
- **Benefits**:
    - Dramatically reduces `songs.cpp` size.
    - Allows loading songs from SD card or Serial in the future.
    - Makes song creation easier (filling an array vs. writing C++ logic).

```cpp
struct SongPart {
    uint32_t duration;
    void (*fxFunction)(...);
    // ... parameters
};
```

### Medium Priority: Encapsulation & Namespaces
Move away from global `extern` variables.
- **Proposal**: Create "Manager" singleton classes or namespaces.
    - `MidiManager`: Handles NimBLE and MIDI input.
    - `DisplayManager`: Wraps `FastLED_NeoMatrix` and provides high-level drawing primitives.
    - `PowerManager`: Handles Lipo voltage checking.
- **Benefits**: Prevents name collisions and clarifies where state is owned.

### Medium Priority: Effect Modularization
Separate animation logic from song logic.
- **Proposal**: Create a standardized `Effect` interface.
- **Benefits**: Allows layering effects and easier testing of individual animations.
